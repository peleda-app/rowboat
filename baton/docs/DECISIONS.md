# Decisions

Implementation decisions made while building, with the reason. Product decisions the maintainer made are under "Decided" in [QUESTIONS.md](QUESTIONS.md).

## 2026-11-25 — phases 0–1

- **One record store contract.** The planned separate `CasRecords` trait and `StateStore` are one thing: `baton-state::StateStore` (small records, compare-and-swap, durable `Ok`). `lease-cas` runs over it, Baton's own state will go through it, and Skein's `ControlStore` implements it in Peleda. One concept less, one implementation of compare-and-swap semantics, one conformance suite.
- **No `lease-single` crate.** Single-process leases are `lease-cas` over `baton-state-memory` (tokens never fall below the wall clock, like Skein's `ownership-single`). Writing a second implementation of the lease rules would have broken the rule of one implementation per function.
- **The lease rules are a pure state machine** (`baton_lease::record`), applied by every implementation (today `lease-cas`; later `lease-quorum` and `lease-server`, which reuses `lease-cas` on the server). Implementations only read, apply, compare-and-swap and retry; they cannot disagree about who wins.
- **Handover reserves the lease.** `request_takeover` records the stronger requester; on release the pending takeover becomes a reservation, so a weaker node cannot grab the key in the gap; a reservation for a node that is no longer alive does not block.
- **Corrupted state grants nothing.** A stored lease record that fails to decode, has unknown fields or version, or breaks an invariant yields `LeaseError::Corrupted`; it is never overwritten. A token at `u64::MAX` refuses new grants instead of wrapping to a low value (a stuck key is a visible outage; a wrapped token would be two writers).
- **Heartbeats count only for their own node** (superseded in part below: liveness no longer reads heartbeat timestamps at all). A heartbeat only counts in the record named after its own node. Heartbeats and lease records are not signed yet; signing and the `lead` capability check come with `baton-group` (phase 4).
- **Signals are bounded.** 64 KiB per payload or value, 200-byte names, and `signal-local` refuses with `SignalError::Full` beyond its limits (tightened below to a byte budget).
- **Copied crates renamed for an open library.** `peleda-seal`, `peleda-mesh-identity`, `peleda-link*` became `baton-seal`, `baton-identity`, `baton-link*`; tenant became group (`GroupId`, `Roster::group`, `IdentityError::GroupMismatch`); the signature and sealing context strings became `baton-seal/v1`, `baton-roster-v1`, `baton-invite-v1`, `baton-join-v1`, so data sealed with the app's old labels does not open with the new ones (nothing was released). The ALPN prefix became the application's choice (`IrohConfig::alpn_prefix`, `baton` by default; Peleda sets `peleda`).
- **`unsafe_code = "forbid"`** across the workspace, and `scripts/check-unsafe.sh` in `mise run check`; Baton has no platform FFI to excuse an exception.
- **Load and fuzz from the start.** `tests/load` (contention, handover, fan-out, churn; small versions run in `cargo test`) and `fuzz/` (lease records, rosters, pairing messages, sealed envelopes, names) exist before any consumer, per the test rule in AGENTS.md.

## 2026-11-25 — after the first adversarial review

An independent review of phases 0–1 found fourteen issues; every confirmed one is fixed with a regression test (see `crates/lease-cas/docs/README.md`, "Tests").

- **Liveness is judged on the observer's clock, by version changes.** The first version compared a heartbeat's timestamp with the observer's clock, so a node with a skewed clock could steal a live lease. Now an observer only notes when a node's record version last changed on its own monotonic clock; heartbeat timestamps are for display. `Liveness` gained `ttl_ms()` and a group argument (liveness of one group never counts for another), and every node runs its own `CasLiveness`.
- **Holder self-expiry is defined** by that rule: stop `ttl` minus a margin after the start of the last successful heartbeat. Leases have no per-lease duration.
- **Waiting requesters expire and keep priority.** A pending takeover or reservation stops blocking when the record has been unchanged for one time-to-live as the observer sees it, or when the requester may not lead; asking again refreshes it. When a holder dies with a stronger node waiting, the key goes to that node, not to whoever calls first. Nodes that announce `can_run = false` count as gone for leases.
- **Tokens use the wall clock in microseconds as a floor, always.** With milliseconds and a per-process counter the floor drifted ahead of the clock under load, so tokens after a restart could be lower; and a lost record reset tokens to 1. `FenceFloor` was removed: one rule for every store.
- **Paging continues until an empty page**, and the `StateStore` contract says a short page is not the end; the state suite now also pages from a missing name.
- **`RecordName` forbids segments starting or ending with `.` and Windows device names**, so names cannot alias on NTFS.
- **`signal-local` is bounded in bytes**: 64 MiB of values, 1,024 topics, channel capacity 16; worst case about 1 GiB, stated in its docs.
- **Suites got stricter**: exactly one winner among live racers, exact time-to-live boundaries, future and past heartbeat stamps, a property test with class changes, staleness and forged releases by node, and no lease without a write except renewals. The churn load test now fails if a holder is replaced before a full time-to-live of silence, and the CI versions of load tests check invariants only.
- **Fuzzing covers store records**: arbitrary heartbeat and lease bytes through `CasLiveness` and `CasLeases`.

## 2026-11-25 — phase 5 (mesh crates moved from the app)

- **`Opener::open(raw, sender)` checks, then commits.** The caller passes the key that delivered the bytes (the stream's authenticated peer) or `None`; every check (size, channel, destination, sender, membership, signature) runs before the replay counter moves. `mesh-link` now uses one opener for all streams instead of one per peer. `MAX_FRAME` lives once, in `baton-mesh`.
- **`baton-mesh` has a conformance suite**, run by `mesh-memory` and by `mesh-link` over both `link-memory` and `link-iroh`.
- **`MAX_PAYLOAD` of the mesh is 72 KiB**, so a full 64 KiB signal plus its envelope fits in one frame.
- **`signal-mesh` wraps a local `Signal`** (normally `signal-local`) and only adds fan-out, instead of keeping its own maps: one implementation of bounded local signals, and remote members are bounded by its limits. It serves one group, clamps remote time-to-lives to 24 h, and does not share counters.
- **`liveness-mesh` stamps heartbeats at observation.** Heartbeats carry a per-sender counter (starting at the wall clock in microseconds), never a time; a new counter is stamped with the `now` of the next `alive` call, so the observer's clock is the only clock, and replayed or older heartbeats never revive a node.
- **`lease-quorum` applies the shared lease rules** inside CASPaxos rounds, keeps acceptor state in a `StateStore` written before every answer, versions registers by content hash, and floors tokens at the highest token any promise reported. It is not Byzantine-tolerant until lease records are signed (phase 4).
- **Freshness joins liveness in the lease rules.** A holder is gone only when the liveness view says so *and* its record has not changed for a whole time-to-live (covering a view that has not yet heard of a new holder); a waiting requester blocks for at most two time-to-lives after the last change (one for the holder to be declared gone, one to take over). Every record write raises `seq`, so content-versioned stores see every write. The token rule is one function, `record::next_token`, used by both implementations.

## 2026-11-25 — after the review of phase 5

- **A heartbeat succeeds only with a majority of acknowledgements, and acceptors veto takeovers they cannot confirm.** The review showed a holder cut off from the majority kept "successful" heartbeats while the majority granted its key to another node, so two nodes acted. Now the cut-off holder's heartbeat fails (it must stop within the time-to-live), and an acceptor refuses to move a key away from a holder it still sees alive or freshly written; the two majorities intersect. The veto judges the transition the proposer makes from the register it read (`base` in `Accept`), so decided values still spread to acceptors that fell behind, and releases always pass.
- **Ids are never Windows device names.** `baton_core::reserved_name` is the one check, used by ids and `RecordName`; a property test proves every valid id forms a valid record name. A member could crash another node's acceptor with a key named `nul` before.
- **Ballots and tokens are bounded.** A ballot may jump at most 2^20 rounds above the binding promise, promises to proposers outside the roster stop binding, rounds never overflow, and registers with tokens more than a day ahead of the clock are refused, so one member cannot burn a key.
- **Resources a member can make another node spend are bounded**: a per-member rate limit on prepare and accept, an acceptor cache that drops idle keys, bounded subscriber buffers, and concurrent sends with timeouts for replies, rounds, heartbeats and signals.
- **Restarted senders are heard again**: `Opener::reset` on every new authenticated stream, and boot epochs in heartbeats, so a node whose clock went back is not locked out.
- **The mesh suite keeps a revoked node on its old roster**, so a transport that only checks on the sending side fails it.

## 2026-11-25 — phase 4 (groups, keys, recovery)

- **HPKE with X-Wing from the `hpke` crate** (0.15, MIT OR Apache-2.0), the same crate and version the app's push payloads already use, for every key box; no hand-made KEM combiner.
- **`baton-keys` is separate from `baton-group`**: boxes and recovery derivation are pure key material other crates may need (push, drop); the log rules live in `baton-group`.
- **The group log is ordered by the store**: entry `seq` is written with `put_if_absent` at `group/{seq}`, so on a shared store with honest conditional writes the store is the arbiter, and the loser of a race gets `Fork` and reloads. Devices-only groups will order it through `lease-quorum`-style rounds later.
- **Key epochs are sealed to exactly the authorized recipients, and the log enforces it**: a `KeyEpoch` with a missing, extra or duplicate recipient, or a secret key for someone who may not lead, does not apply. Anyone verifying the log can see who holds which epoch, which is what `needs_rotation` uses.
- **`ShareEpoch`** gives a member's new device past epochs (boxed by any node with read), only to recipients authorized now and missing; it is how history stays readable without re-encrypting.
- **Recovery recipients get both keys**: a member's recovery key for every resource that member reads, the group's for every resource, so a restore can open provider credentials too.
- **`RekeyMember` was added** after the recovery drill showed the gap: with every device lost the member key is lost too, and a new device's certificate must be signed by a member key. The member's recovery key moves role, recovery key and grants to a new member key; old nodes stop counting.
- **No PAKE and no ML-DSA in this phase**: pairing keeps the copied invite flow (128-bit secrets in a QR code), and signatures stay Ed25519; both are open questions in QUESTIONS.md.

## 2026-11-25 — after the review of phase 4

The review found that a node with no member key could become owner through recovery rotation, that the group recovery key received private resources' keys, that readers' recovery keys received secret keys, and eleven more issues. All are fixed with a regression test each (`crates/group/src/review_tests.rs`):

- **Recovery keys rotate only by themselves** (member's by the member's current recovery key, group's by the group's), and every recovery public key is self-signed (the signing key signs the KEM key), so nobody can pair a victim's recovery signing key with their own KEM key.
- **The group recovery key covers shared resources only** (more than one member involved); a member's recovery key gets the secret key only if that member may lead. This is what SECURITY.md promised.
- **Blind nodes hold nothing**, whatever the grants.
- **Entry times never go back**, and fresh entries from the future are refused (`apply_fresh`), so expired certificates cannot be revived by backdating.
- **Epochs carry commitments to their keys**; `open` skips boxes whose keys do not match, sharing secret keys needs lead or admin, and re-sharing to a recipient is allowed, so nobody can poison an epoch for a new device or a recovery key.
- **Losing lead forces a new epoch** (epochs record who got the secret key).
- **Every key is used once, in one role, for the life of the group** (member, node, recovery signing and KEM keys), and node certificates are co-signed by the node, so keys cannot be squatted or recycled.
- **Admins add plain members only and cannot revoke owners' nodes**; owners add admins and owners (as SECURITY.md says).
- **Grants to one's own member need to be the creator**: owners cannot grant themselves into members' private resources, resource admins cannot grant themselves read.
- **`store::load` checks the group, `load_expecting` checks the genesis fingerprint**, and decoding refuses non-canonical bytes.
- **Applying entries checks first and mutates in place**, so verification is linear.
- **Still open (documented)**: a class filter for member grants ("desktops and servers, not phones") and a "since the grant" rule for sharing past epochs.

## 2026-11-25 — phase 6 (commands and peer fetch) and its review

- **`baton-command`**: commands are signed by the issuing node and sealed under the resource's data key of a named epoch; the leaseholder's `check` validates everything against its own current group log, so a revocation it knows of applies at once. Results are signed by a node holding `Lead`. Deduplication, claim-before-execute and `Uncertain` stay in the worker's durable queue (Skein); delivery is at least once over mesh channels `baton/command/1` and `baton/result/1`.
- **`baton-fetch`**: objects by BLAKE3 content id over link protocol `fetch`; peers in the caller's order, then the application's `Source`; every answer verified; refusals look like misses.
- **Review fixes** (one regression test each): the sealed payload and outcome are bound to the whole command or result body, and `check` takes the resource the leaseholder expects, so a payload never opens as another resource's or class's command; `check` re-validates class, idempotency key, the time window (at most a day, not from the future) and the epoch; the idempotency key is sealed with the payload and deduplication is keyed by issuer, resource and key; result checks take the issuer's `now`, so expired leaders' results are refused; `serve` reads the request under a short header timeout before taking a shared slot, caps requests per peer and bytes in memory; the `Fetcher` reads bodies in chunks, marks liars per resource for a limited time, de-duplicates peers and bounds the source; `LocalObjects` must answer per resource.

## 2026-11-25 — phase 8 (drop, wake, lease-server, batond)

- **One implementation of the drop rules, in the `baton-drop` library.** The wire codec, admission, replay cache, quotas, time-to-live, long polls (`DropService`) and the client (`DropMailbox` over an `Exchange` seam) live there with no file, database or network I/O; `mailbox-memory` is that client over an in-process exchange, and `mailbox-drop` will be the same client over HTTP, so the mailbox suite exercises the same code the server runs.
- **`wake-drop` is `wake-mailbox`**: a wake is a `put` into the target's wake box, `listen` a long-polled `take` plus an immediate `ack`; it needs nothing from drop, so it works over any `Mailbox`.
- **Box keys are derived per box**: `BoxKey::derive(seed, box, role)` is BLAKE3 `derive_key` over a 32-byte seed from the node's `SecretStore`, the box id and the role, so the operator cannot link a group's boxes by key. The contract takes `BoxKey`s, not node identities.
- **`create` takes the box id**: the reader picks the random id first because its reader key is derived from it.
- **Requests are signed by the box key** under context `baton/drop/request/1` and the operator's realm (from the client's own configuration, never from the service), carry a version byte, operation, box, client timestamp, 16-byte nonce and BLAKE3 of the body; freshness ±5 minutes on the service's clock, inclusive.
- **Check, then commit for the replay cache**: only requests that passed the signature, the role check and admission record their nonce, so strangers with free keys cannot fill it; when full of fresh nonces it refuses with `Busy` rather than evicting one. It is in memory; after a restart one replay of a request from the last five minutes is possible and harmless by construction (see `crates/drop/docs/README.md`).
- **Writer changes are versioned** (the client's clock in microseconds, increasing per client; the store refuses a version not above the stored one), so a replayed older writer list cannot restore a removed writer even with an empty replay cache.
- **Proof of work is argon2id hashcash** (`argon2` 0.6) over label, box id and nonce with the operator's salt; caps on both sides (difficulty ≤ 24, memory ≤ 4 MiB, ≤ 3 passes) keep a verification to one cheap evaluation and stop a hostile service from demanding unbounded work; verifications run on blocking threads, four at once. Tokens are kept as BLAKE3 hashes and compared in constant time over every configured token. `argon2` and `blake2` build at `opt-level = 3` in the dev profile so tests do not crawl.
- **Boxes idle for their time-to-live disappear**: a box the reader has not used (create, take, ack, writer change) for its time-to-live is treated as absent and swept, so abandoned boxes free storage; readers take at least once per time-to-live (default 14 days).
- **Expired messages never count**: quotas are checked after removing the box's expired messages, so a full box of stale messages accepts new ones.
- **Takes are bounded twice**: at most `max_take` (256) messages and `max_take_bytes` (4 MiB, always at least one message); waiting takes are capped in number (`max_waiters`) and duration (`max_wait`, 30 s); a deletion wakes waiters.
- **Long polling only**; no WebSocket.
- **HTTP adds no format**: `drop-http` has two routes, `GET /v1/info` and `POST /v1/request`, carrying raw `baton_drop::wire` bytes; refusals by the service travel as `200` with an encoded error, and other statuses (`413`, `408`, `429`, `503`) mean the request never reached the service. HTTP/1.1 only: hyper's header timeout covers every request on it, and HTTP/2 brings nothing for one request per long poll.
- **HTTP limits** (each with an attack test on 127.0.0.1): body size from `DropService::max_request` (declared or counted, chunked included), header and TLS-handshake timeout 10 s (handshakes run off the accept loop), body timeout 10 s, service deadline `max_wait + 10 s`, 4,096 connections, 2,048 requests in flight refused at once (never queued), and per client (IPv4 address or IPv6 /64) a token bucket of 20/s with burst 100 and 16 requests in flight, long polls included. The limiter table is bounded (65,536 clients): idle entries are dropped at most once a second, and when none is idle new clients share one overflow budget, so an address flood costs memory once and cannot evict busy clients. Behind a proxy the client is the last `X-Forwarded-For` entry (the nearest proxy's), off by default.
- **Logs carry no box ids, keys, content or addresses**; `drop-http` logs only connection errors at debug level. The test that captures every event runs alone in its own binary, because `tracing`'s per-thread default subscriber races other tests' callsite caching.
- **`mailbox-drop` is the `baton-drop` client over a reqwest `Exchange`**: HTTPS required except to loopback (or with `allow_http`), no redirects, no proxy, no credentials in the URL, HTTP/1.1, timeouts of `wait + 15 s`, replies read in chunks and capped by the service's info (`max_reply`), statuses mapped to `MailboxError` with fixed messages (no URL or address in errors). The paths are restated in the client so it does not depend on the server crate.
- **Persistent store formats live in `baton_drop::record`** (versioned box record, `box id ‖ id` big-endian message keys, `stored_at ‖ bytes` values) with strict decoders and a fuzz target (`drop_record`), so every persistent store reads back the same way and a corrupted record is a backend error.
- **redb 5** (the current release, MIT OR Apache-2.0, already in the local registry) instead of the 2.x/3.x the brief named. `RedbDropStore` lives in `apps/drop` (no library opens files); each call is one transaction on a blocking thread; marking a box used on a take commits without a flush; idle boxes are removed by writes and the sweeper, reads only hide them; expired messages are pruned from the front of a box (ids grow with time). Store-wide caps (`max_boxes` 100,000, `max_total_bytes` 8 GiB) answer with a quota error, kept in a `totals` table updated in the same transaction.
- **`apps/drop` (package `baton-drop-service`, binary `drop`)**: TOML with unknown keys refused, plus flags; admission by an operator token file that must be `0600`, proof of work whose salt is generated once and kept in the store, or `open`; data directory `0700`, store `0600`; TLS with rustls (aws-lc-rs, ALPN `http/1.1`, key file `0600`) or plain HTTP on loopback behind a TLS-terminating proxy; graceful shutdown waits `max_wait + 5 s`; the sweeper runs every 5 minutes. The library target's `start(config, clock)` is what `batond` will embed.
- **Load `drop_http`**: 200 boxes × 100 messages over HTTP on 127.0.0.1, 32 boxes at a time so it fits the default file descriptor limit on macOS; expects 20,000 messages/s (measured about 120,000 to 150,000 in release).
- **`lease-server` reuses `lease-cas` on the server** (`CasLeases` and `CasLiveness` over the server's own `StateStore`), as the plan says, although implementation crates normally depend only on their contract: the lease rules then exist once, and the crate adds only the link protocol, authorization and limits.
- **The server is the single liveness observer for its clients.** `CasLiveness` keeps observations per instance, so one instance belongs to one observer: the server writes every client's heartbeat into its store and judges `alive` on its own clock; the `now` a client passes is ignored. `RemoteLiveness::valid_until` gives the holder's self-expiry (start of the last confirmed heartbeat plus the server's time-to-live minus a margin), and a failed heartbeat extends nothing. The liveness conformance suite runs through the server with its clock driven to the observer time the suite passes.
- **Lease protocol `lease`**: `u32` length ‖ `[1] ‖ postcard`, requests at most 1 KiB, replies at most 1 MiB, no trailing bytes, ids checked while decoding; persistent request/reply streams (a client keeps up to 4, retrying once on a new stream when a reused one broke, since every request is safe to repeat). Frames are not signed: the link authenticates the peer by key on every stream, as for `fetch`.
- **Who may ask what is the `Authorize` trait**, asked on every request: `node(peer)` (default the key's node id), `member(peer, group)`, `profile(peer, group, profile)`, `lease(peer, group, key)`. A request naming a node must name the peer's. This refines the planned `authorize(peer, group, key)` callback so batond can also cap a profile's class at the certified one and refuse revoked nodes at once.
- **Lease server limits**: idle stream 60 s, rest of a frame after its first byte 2 s, reply read 5 s, decision 10 s, 1,024 streams in all and 8 per peer (more are closed at once), 256 decisions at once with 1 s wait for a slot; malformed or oversized frames close the stream, an unknown version is answered with `Refused(Version)` first. No per-peer request rate limit beyond the stream caps.
- **Load `lease_server`**: 32 clients × 2,000 keys over the in-memory link; expects 2,000 remote acquires/s (measured about 11,000 in release, the same as `lease-cas` directly, since `alive` reads dominate).
- **Group logs on a server are `baton-group-server`**, a library like `lease-server` (no storage of its own: logs go through `baton_group::store` into the caller's `StateStore`), so a non-blind server built on `baton-node` can hold a log the same way; `batond` only composes it. Protocol `group`: `u32` length ‖ `[1] ‖ postcard`, requests `Hello`, `Head`, `Fetch { after, limit }`, `Push { entry }`, requests at most `MAX_ENTRY` + 256 bytes, replies at most 4 MiB, fetches at most 256 entries (always one), frames unsigned because the link authenticates the peer and every entry carries its own signature.
- **Each held group is pinned to its genesis hash** in batond's configuration (the recovery-sheet fingerprint): before genesis only that entry is accepted, a store with another genesis refuses to load. Pushes are checked at the head by `GroupLog::apply_fresh` (skew 5 minutes on the server's wall clock), applied in memory, then written with `put_if_absent`; a failed write reloads the group from the store (held empty, so nobody counts, if that fails too). An exact repeat of a held entry succeeds with `new: false`; a different entry at a held position is `Fork`, past the head `Chain(head)`. At most 100,000 entries per log.
- **Who reaches a log**: counting nodes of the group (certified, not revoked, member in the group, not expired, on the server's clock), plus per-group bootstrap peers from the configuration (the founding node before genesis, a recovering device, removed once certified). There is no open window before genesis. After an entry that can take trust away (`RevokeNode`, `RemoveMember`, `RekeyMember`) the server severs untrusted peers at once; every request is authorized again anyway.
- **batond's lease authorization from the log** (`Rules`, implementing `Authorize`, `Trust` and `Admit`): `node(peer)` only while the peer counts in some held group; `member` while it counts in that group (blind nodes included, they may read liveness); `profile` only for a non-blind node announcing a class no stronger than its certificate's; `lease` only for a non-blind node with `Lead` on the key's resource. **A lease key maps to one resource**: the key itself, or the part before the first `--` when a non-empty suffix follows (`vault-1--sync` → `vault-1`); a resource id containing `--` cannot be leased through batond, and `x--` maps to none. Lease ids allow only `[a-z0-9_-]`, so a separator from that alphabet was needed; taking the first `--` keeps the mapping a function, so a node with `Lead` on `a` can never hold a key that belongs to resource `a--b`'s jobs under another reading.
- **`batond` stores in redb** (`RedbState`, inside `apps/batond`, passing `baton_state::testing::state`): records `group ‖ 0x00 ‖ name` → `version ‖ value` with versions from one store-wide counter (no version ever repeats for a record, even after a delete), one flushed transaction per call on a blocking thread. One `state.redb` holds group entries (`group/…`), lease records (`lease/…`) and heartbeats (`nodes/…`).
- **The node key is a file**: `node.key` in the data directory (created `0700`), 32 raw secret bytes created with `create_new` and mode `0600`; a key readable by group or others, of the wrong length or not a regular file is refused. It is batond's only secret: no member key, no KEM secret, no resource key, no `SecretStore`. The group certifies its public half as a `Blind` node; members pin it for the link.
- **One process**: iroh (`link-iroh`, trust from `Rules`, relays and discovery off unless configured, post-quantum key exchange required unless `allow_classical`), the group and lease servers on it, and `baton_drop_service::start` for the optional `[drop]` section (the whole `apps/drop` configuration). Stop order: group and lease streams, the link, then the drop service with its grace period. TOML with unknown keys refused, 1 to 1,024 groups.
- **Deferred from batond**: an embedded iroh relay (run `iroh-relay` beside it), wake sending (members wake each other through `wake-mailbox` over its drop service), adding groups without a restart, and holder-signed lease records.
- **Load `group_server`**: 2,000 pushed node certifications, then 16 members syncing and verifying the whole log at once over the in-memory link; expects 5,000 entries verified/s (measured 30,000 to 37,000 in release; pushes about 2,200/s, each verified by client and server).

Phase 8 review (one regression test per finding, written before the fix):

- **security-1, a log full of a member's entries blocks revocations**: `GroupLogs` takes `LogLimits { max_entries, max_bytes, reserve }`; beyond either limit only entries that take trust away (`RevokeNode`, `RemoveMember`, `RekeyMember`) signed by an admin's or owner's node or a recovery key are stored, up to `reserve` entries and `reserve × 4 KiB`. batond: 100,000 entries, 256 MiB, reserve 1,000. Pushes are rate limited per peer on the server's clock (20/s, burst 100, `Refused(Busy)`). A plain member cannot revoke its own lost device once the log is full; an admin or owner does it.
- **security-2, one box fills the global replay cache**: the cache keeps a share per box (`replay_per_box`, default 4,096). Not done: a tighter future skew (the window stays ±5 min; expiring entries at `min(at, now) + freshness` would allow replays of future-stamped requests), and charging `Busy` refusals to the HTTP client.
- **security-3, clients that never read hold connections**: `drop-http` wraps every connection in a write deadline (`write_timeout`, 30 s without progress) and caps connections per client (`max_connections_per_client`, 64, only with `ClientIp::Peer`).
- **security-4, long polls starve short requests**: a waiting take moves from the in-flight budget to a long-poll budget (`max_polls` 1,024, `RateLimit::polls` 4 per client) and the service caps waiters per box (`max_waiters_per_box` 4); without room a take returns at once (`DropService::handle_with(raw, false)`), never `503`. `wire::wait_ms` peeks at the take unverified, only to choose the budget.
- **security-5, cheap boxes exhaust the store**: boxes admitted by proof of work or on an open service get `DropConfig::untrusted` quotas (1 MiB, 1,000 messages, 7 days); the store keeps `Admitted` per box (`DropStore::create` takes it, box record version 2) and `RedbDropStore` caps their share (50,000 boxes, 2 GiB). Deferred: binding proofs to a time epoch or rotating the salt.
- **security-6, revoked bootstrap peers keep access**: `Rules` admits a bootstrap key only while the log has no genesis or never certified it (`GroupState::was_certified`), in `Admit` and `Trust` alike; this replaces "removed once certified" as an operator duty.
- **security-7, expired box ids can be squatted**: a box id is `BoxId::of_reader(reader)` (BLAKE3 `derive_key("baton/drop/box/1", reader)`) and `create` refuses any other id with `Denied`, in the mailbox suite too. This replaces "the reader picks the random id first": `MailboxWake::new(mailbox, seed, slot)` derives the reader key from seed and slot and the box id from the key.
- **security-8, ambiguous lease keys**: `resource_of` maps a key to none when the resource part ends with `-` or the suffix starts with `-`. `CreateResource` ids are not restricted in `baton-group` (application-agnostic); such resources are leasable through batond only whole. An explicit resource field in `LeaseKey` is deferred.
- **correctness-1, a holder without `Lead` cannot release**: `lease-server` allows a release to the lease's own node without asking `Authorize::lease`. Losing `Lead` does not end an existing lease by itself (deferred): the holder is expected to release when its log shows the change; one that does not keeps it until revoked or silent.
- **correctness-2, a restart with a shorter TTL**: heartbeats are answered `Beat { ttl_ms }` and `RemoteLiveness::valid_until` uses the time-to-live of that confirmation; `ServerConfig::previous_ttl_ms` makes the server judge with `max(ttl, previous)` for the whole run. batond keeps `lease.ttl` (advertised, the older floor and until when on the wall clock) so quick successive restarts still honor the old value.
- **correctness-3, stale wake cursor**: `MailboxWake::listen` always takes from the front of the box (acknowledged wakes are gone), so a re-created box is read from id 1.
- **correctness-4, one huge sweep transaction**: `RedbDropStore::sweep` runs short transactions of at most 256 boxes and 4,096 messages, resuming after the last box key; a handler deadline in `drop-http` answers `504`, which `mailbox-drop` maps to `Unavailable` (outcome unknown), not `Busy`.
- **correctness-5, a cancelled push after `apply_fresh`**: `GroupLogs::push` (now `self: &Arc<Self>`) runs on its own task, so the request timeout or `stop` cannot drop it between memory and store.
- **rules-5**: the batond e2e test and the group-server suite build the revoked node's entry on the current head and expect `Invalid` and an unchanged head.
- **rules-6**: TRANSPORTS says batond embeds the drop service.

## 2026-11-26 — no heartbeats in object storage for Peleda

- **Why:** with `CasLiveness` over S3 every node writes a heartbeat per interval and every lease check lists and reads every heartbeat; 10 nodes at 10 s cost about $36 a month on AWS before any account, and each account added about $2.4 a month, because `CasLeases` asked liveness on every call.
- **Peleda never uses `CasLiveness`.** `peleda-sync` uses `lease-server` where the group has a server, otherwise `lease-cas` with `liveness-mesh`, or `lease-quorum` without a bucket. With `liveness-mesh` the store sees no heartbeat, a holder's renewal is one read of its lease record and no write, and writes happen only when a lease changes hands. `crates/liveness-mesh/tests/with_lease_cas.rs` runs the lease suite on this combination, counts store calls (no write, no listing, one read per call while holding) and checks that an isolated holder learns its heartbeats failed while the majority takes over with a higher fence.
- **`CasLeases::reuse_alive_for(ms)`** for deployments that do keep heartbeats in a store (plain Skein servers sharing a bucket): one liveness answer per group per interval, at most a quarter of the time-to-live, reused only while it lists the caller and every node the record names, so reuse can delay a takeover but never cause one. Tested with the lease suite, a call-count test and a dead-holder test.
