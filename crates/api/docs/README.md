# rowboat-api

The contract of the node's whole surface for an app: `NodeApi`, its requests, responses and events, `NodeError`, the checks every caller and the node run, the cursor codec and the request payloads reserved for Baton commands. The app's core holds only `Arc<dyn NodeApi>`; `rowboat-node` implements it in process.

## Ids

| Id | Form |
| --- | --- |
| `AccountId` | `a` and 26 characters of `[a-z2-7]`, generated by the node |
| `MailboxId` | the provider's id (IMAP: the decoded path), 1 to 1024 bytes, no control characters; `Debug` shows the length |
| `MessageId` | 64 lowercase hex: the BLAKE3 of the original bytes |
| `ThreadId` | positive; may vanish when threads merge (`NotFound`, reload the list) |
| `CommandId`, `DraftId` | canonical ULIDs |
| `Tag` | `[a-z0-9._-]{1,64}` (`spam.junk`, `category.person.direct`) |
| `EmailAddress` | `plausible_address`: one `@` with text on both sides, at most 320 bytes, none of whitespace, control characters, `<>,;"()\[]:`; `Debug` shows the length |

Every id checks itself when built and when deserialized, so a payload with a malformed id never reaches the node.

## Operations

`node_info`, `discover`, `add_account`, `update_password`, `update_account`, `remove_account`, `list_accounts`, `sync_now`, `list_mailboxes`, `list_threads`, `get_thread`, `list_messages`, `get_message`, `message_raw`, `set_read`, `set_flagged`, `move_to`, `archive`, `delete`, `save_draft`, `list_drafts`, `get_draft`, `delete_draft`, `send`, `cancel_send`, `outbox`, `search`, `suggest_addresses`, `knows_address`, `events`, and the group (`docs/GROUP.md`): `create_invite`, `cancel_invite`, `inspect_invite`, `accept_invite`, `adopt_server`, `grant_to_server`, `confirm_pairing`, `list_nodes`, `rename_node`, `revoke_node`, `group_status`. What each does is in the trait's docs and in `docs/NODE.md` "Commands".

Guarantees of every implementation:

- Requests pass `check` first (`check::setup`, `password`, `patch`, `list`, `targets`, `targets_of_one_account`, `draft`, `sendable`, `search`, `suggest`); a broken rule is `InvalidInput` and changes nothing. Unknown accounts, threads, messages, drafts and commands are `NotFound`.
- Lists are newest first, at most 200 rows (`MAX_PAGE`), with an opaque `Cursor`; following `next` gives every row once while nothing changes.
- Mutating calls queue one command per account and mailbox and return their ids; a target the node does not know goes to `Queued::skipped`. The effect shows in reads at once (pending changes) and settles with `CommandSettled`.
- Errors (`NodeError`) and events (`NodeEvent`) carry kinds, ids and counts only. The node maps Skein's typed causes onto them: authentication failed is `AuthFailed`; TLS is `TlsFailed`; plain text or a missing STARTTLS is `InsecureRefused`; unreachable, broken, timed out (and a send that broke before the message was complete) is `ServerUnreachable`; quota and a message too large are `QuotaFull`; refused, unparsable, unknown mailbox and recipients refused are `ServerRefused`; throttling keeps its wait; bad settings are `InvalidInput`.
- `discover` returns `Candidate`s with `source` (`table`, `autoconfig`, `srv`, `guess`), `verified` (both servers answered a probe) and `needs_confirmation` (a server outside the address's domain and the known providers: show it as "suggested by" its source and ask). Secrets enter only through `add_account` and `update_password` and are never returned.
- `events()` is bounded (`EVENT_BUFFER`, 256); a subscriber that falls behind gets one `Lagged { missed }` and the node never waits for it. `NewMail { account, items }` names at most `MAX_NEW_MAIL` (64) arrivals the notification policy wants shown (`Attention::Alert` or `Silent`, `show_sender`, `show_subject`), ids only.
- Pairing: `create_invite` returns a `PairingInvite` (id, QR payload, expiry); `accept_invite(code, address)` takes a QR payload or a short code with the pairing address beside it and returns a `PairingResult` (`restart_required` after joining another group). Fingerprints arrive on `group_events()` as `GroupEvent::PairingCheck { pairing, fingerprint, node, class, confirm }`; when `confirm` is set the app answers with `confirm_pairing`. Pairing failures have their own kinds (question 58, 2026-11-27): `PairingCodeRejected` (a wrong, used, withdrawn or unknown code, which the joiner cannot tell apart by design), `PairingExpired` (a QR invite past its expiry by this node's clock, refused before anything is dialed; an invite of this node that expired unused), `PairingRefused` (the other side said the fingerprints differ, did not answer, or would not take this node), `Forbidden` (no member key, or the log does not allow it), `PeerUnreachable` (the other node could not be reached). `inspect_invite` says whether a code is a device or a server invite and when it expires, without dialing. `adopt_server(code, address, accounts)` grants the server exactly the chosen accounts (plus the group's storage); `grant_to_server` adds accounts later (question 65). `rename_node` names a node on this node only (`group::node_label`, 1 to 64 characters, one line). `NodeSummary` carries `last_seen` (since this node started) and `may_lead`. `group_status` gives `ServerState` (`none`, `answering`, `silent`) and the leader of every account this node reads; `GroupEvent::LeadersChanged` asks to reload it. `PairingInvite` has `short_code` and `address`, which device invites leave empty until a rendezvous exists (question 46). `list_nodes` gives `NodeSummary` rows sorted by node id; `revoke_node` returns `Revoked { secrets_rotation_required }`. `GroupEvent::NodesChanged` and `NodeRevoked` (this node was revoked) tell the app to reload; `GroupEvent::JournalForked { account }` says the journal of an account this node follows forked and is no longer followed; group events are a stream of their own so `NodeEvent` is unchanged for apps that match it exhaustively. The checks are `group::pairing_text`, `invite_id` and `node_id`.
- `AccountInfo` carries the folder settings (`skipped_mailboxes`, `archive_mailbox`) and the `notify` switch; `AccountPatch::notify` turns it on or off.

Limits: 1,000 targets per call, 500 recipients, 100 attachments of 25 MiB in all, 1 MiB of text, 998-character subjects, 200-character names, 980-character message ids (`check::MAX_HEADER_ID`, so `In-Reply-To` fits one line), 200 drafts, 20 suggestions, 256-character search texts.

## Wire helpers

- `cursor::{encode, decode, Position}`: `c1.` and base64url of a small JSON object; `decode` refuses anything this codec did not make and is fuzzed.
- `request::{Request, CommandClass, encode_request, decode_request}`: the mutating calls as JSON payloads for phase 2's Baton commands (`mail-account-add`, `mail-flags`, `mail-send`, ...). Secrets never travel in a request. `decode_request` caps the input at 40 MiB, checks every id and runs the request's checks; it is fuzzed.

## Conformance

Behind the `testing` feature:

- `testing::validation(&api)`: every operation's validation and `NotFound` answers, forged cursors, target limits, hostile search text, draft header injection, malformed pairing codes and ids, revoking oneself or a stranger, the list of nodes holding this node exactly once; error texts free of a canary input. Needs no accounts.
- `testing::seeded(&api, &account)`: on an account with at least three messages, newest-first order, page-by-page paging without repeats or gaps, threads, a mark-read that shows at once and back, unknown targets skipped, original bytes readable.
