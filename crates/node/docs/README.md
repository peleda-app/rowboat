# rowboat-node

Peleda's node builder (RULES.md MOD-4): it picks Skein's and Baton's implementations for a profile, receives everything platform-specific from the app (keystore, content pipeline, data directory) and answers `rowboat_api::NodeApi` in process. The spec is `docs/NODE.md`; where they differ, this file describes the code.

```rust
let node = Node::builder()
    .profile(Profile::Desktop)
    .data_dir(app_data_dir.join("node"))
    .keystore(keystore)            // Arc<dyn rowboat_keystore::Keystore>
    .content(content)              // Arc<dyn rinse_mail::Content>, the app's sandboxed workers
    .build()
    .await?;
let api: Arc<dyn NodeApi> = node.api();
node.start().await;                // engine, follower, housekeeping
node.shutdown().await;             // stops them, releases every lease, closes the directory
```

`shutdown` stops the engine (a worker still busy after the profile's shutdown time, 30 s on the desktop, is aborted), the follower and housekeeping (aborted after twice that), the group's tasks and the node's background work (a removal resumes on the next start), then closes the data directory once the storage calls in progress finish (`FsObjects::close`). When it returns, a new node can open the directory in the same process even while old `NodeApi` handles exist; they answer storage errors from then on.

Optional: `spam` (default `rowboat-spam-signals`), `category` (default `rowboat-category-bento`), `discovery` (default: the table for every profile; on the desktop also `rowboat-discover-autoconfig` over `rowboat-discover-net::Https` and `rowboat-discover-srv` over `rowboat-discover-net::UdpResolver::system()`, each left out when it cannot be built), `prober` (default `ServerProber` on the desktop, none on the test profile), `providers` (default IMAP and SMTP; required for the test profile unless `test_roots` is set), `clock` (system clock), `endpoints` (where the node binds its link and pairing endpoints: `rowboat-endpoint-iroh` with relays and discovery off on the desktop, none on the test profile, so pairing answers `ServerUnreachable`; tests pass `rowboat-endpoint-memory` or loopback iroh). With the `testing` feature, `test_roots(roots)` (and `ServerProber::with_test_roots`) makes the default IMAP and SMTP providers and the default `ServerProber` also trust a test CA (certificates are still verified, plain text is still refused) and gives the test profile real IMAP and SMTP; the integration suite (`tests/integration`) runs the node that way against containers.

## Data directory, identity and keys

```
<data_dir>/
  objects/   skein-storage-fs root (exclusive lock): every value sealed (XChaCha20-Poly1305)
  view/      view.sqlite (+ -wal, -shm): the mail database, in the clear (question 40)
```

Directories are `0700`; the database file `0600`.

- **First run** over an empty directory: an Ed25519 identity (`baton-identity`) and a random 256-bit master key go into the keystore as `rowboat.identity` and `rowboat.master` (class `Background`); the objects key and the keyring key are derived from the master key with BLAKE3 (`rowboat-node objects v1`, `rowboat-node keyring v1`); a group id (`g` and 26 base32 characters) is registered as Skein's tenant; the node's KEM key (`rowboat.node-kem`), the member key (`rowboat.member`) and the two recovery roots (`rowboat.recovery-pending`, kept until the app has shown them) go into the keystore; the group log's genesis is written through `ControlState` (`baton/group/...`, GROUP.md); and the node record `system/node` (format 2, node id, group, profile, creation time) last. A crash before the record leaves the keys in the keystore; the next start reuses them and finishes.
- **Upgrade from phase 1.** A format 1 record (a roster of one at `system/roster`) is upgraded on the first start: the new keys, genesis for the existing group id, a resource `acct-{id}` with every command class for each existing account, `system/roster` deleted, the record rewritten as format 2 last. Every step is idempotent, so a crash resumes. Moving sealed passwords under resource keys waits for Skein's S3 (wave 2).
- **Later starts** read both keys and the record. A missing key, a key of the wrong length, a key that does not open the record, or a record for another node id is `BuildError::KeysLost`: the node never makes a new key over existing data. A locked keystore is `KeystoreLocked`.
- A missing KEM key under a format 2 record is `KeysLost`; a missing member key leaves a node that reads but cannot invite.
- A directory with anything else in it is `NotEmpty`; a directory another process holds is `Locked`. The lock is released when the node and every API handle are dropped.

## Group

- **Capabilities.** Every account is a resource `acct-{account}` in the group log, created by `add_account` with read, lead, admin and every command class (`mail-account-add`, ..., `mail-send-cancel`) granted to this node's member. Reads need `read`, every mutating call its class; anything the node may not use answers `NotFound`, like an account it does not know (also after this node was revoked or its certificate expired).
- **Pairing.** `create_invite` opens a pairing endpoint for one device invite (closed when it is used up or after 10 minutes) and serves it in the background; when a device answers, `GroupEvent::PairingCheck { confirm: true }` on `group_events()` waits for `confirm_pairing` (2 minutes). `accept_invite` with a device invite joins the inviter's group: only a node with no accounts and no other nodes may (`Busy`), the joined log is stored, the member key replaces this node's, the abandoned group's recovery roots are deleted, the new group is registered as a tenant and the node record moves to it; the instance then answers `Busy` for group calls until the app rebuilds it (`restart_required`). With a server invite (QR, or short code and address) the node adopts the server into its own group after the person confirms, granting every account its member created (`accept_invite`) or exactly the chosen ones (`adopt_server`); `grant_to_server` grants more later. After joining, everything the node kept under its old tenant (`tenants/{old}/`) is deleted and the old tenant leaves the registry. `NodeBuilder::label` sets the name the node gives when it pairs; `rename_node` stores names under `rowboat/names/{node}` in the group's state (local to this node; a name given to this node itself replaces its pairing label). `last_seen` is kept in memory from group exchanges and pairings. `NodeBuilder::advertise` puts the device's LAN addresses into the hints of the default iroh endpoints (question 59); relays and discovery stay off. `group_status` asks the arbiter for each account's holder (3 s at most), else names the node that signed the newest local head; an arbiter change raises `GroupEvent::LeadersChanged`.
- **Link.** The node's own link (its identity, trusting exactly the nodes the log counts) comes up when the group has other nodes or a pairing needs it, serves the group log exchange, and exchanges heads with every peer at start, every 5 minutes and after every local change. A revocation severs the revoked node's streams at once. The node renews its own certificate in its last 30 days.
- **Replication** (`rowboat-sync`, GROUP.md "Journal replication"). The node's journal is attested with its node key (`NodeAttestor`), and its storage reads segments and blobs through its peers after local storage (`skein-storage-tiered` with `PeerTier`). When the link is up, the node serves heads, segments, blobs and commands on it. Every 2 s on the desktop (every follower poll in the test profile) it announces the new heads of the accounts it leads; every 5 minutes (every tick in tests) it asks its peers for the heads of every account it may read and does not lead, follows the newest verified one (stage, fetch blobs, install) and delivers its command outbox. An account it follows gets an account record with `owner` (the leading node) from the owner's description, so every read (`list_accounts`, mailboxes, lists, threads, search, `message_raw`) works on it from the replica; its health stays `unknown`. A fork raises `GroupEvent::JournalForked` and stops following the account.
- **Commands to the owner.** On an account it follows, every mutating call that queues a Skein command (`set_read`, `set_flagged`, `move_to`, `archive`, `delete`, `send`) goes to the owner as a Baton command through the durable outbox; the returned command id is the id the owner queues it under, so the overlay, `CommandSettled` and `SendSettled` settle from the replicated journal exactly as for a local command. A send's message is composed here and fetched by the owner from this node. `cancel_send` and `sync_now` go to the owner too (a cancel is reported `Cancelled` at once; a send that already started settles from the journal). A command the owner refuses, or that expires in the outbox, settles as `Failed { reason }` (`Uncertain` when the owner may have run it). `update_password`, `update_account` and `remove_account` answer `Unavailable`: the owner manages the account. Drafts stay on the node that writes them.
- **Leases across nodes** (GROUP.md, wave 2). While the group has no server node, each node keeps its own `lease-cas` and leads the accounts it added (wave 1). Once a server node counts (the lowest key when several do), it runs `baton-lease-server` on its link, authorized from the group log (only counting nodes speak; a node announces only its certificate's class; it takes or asks to take over only the lease of an account it holds `lead` on), and every other node takes leases and heartbeats there. Leases go to the strongest live node holding `lead` on the account (server, then desktop, then phone; equal classes by weighted rendezvous), through Skein's `RunConfig::eligible`. A weaker holder hands over at a clean point: its worker stops, it exports the account's state (Skein's account record and control records, credentials, cursors, the node's account record, `cmdkey` records, queued commands) sealed with the account resource's secret key and offers it to every node that may lead the account, then releases. The holder (or the node that wrote last) also offers the state whenever its head moves and on every round. A node with `lead` stores an offer sealed after checking it (`rowboat_sync::Replication::receive_offer`) and opens it only when it takes the lease, before the engine claims the log; the claim re-attests the head under the new holder's key and higher token, so the journal continues from the previous holder's last head. A holder that disappears is replaced once the server judges it gone. A node that loses the lease follows the account like any reader; one whose journal ran past the head the next holder continued from (it wrote while cut off) drops its replica of the account and follows again from the start. `Node::set_can_run(false)` (a phone before suspension, a server whose accounts go back to the person's devices) hands everything over and takes nothing until set back. `Node::leads(account)` says whether this node leads an account now.
- **When the server is silent** (GROUP.md, "When the server is silent"). A device that has had no answer from the group's server for the takeover delay (`NodeBuilder::fallback`, `FallbackTiming`: 5 minutes by default, 16 heartbeats in the test profile), or that got the server's signed leaving notice and then found it no longer answering, arbitrates without it: the first device of the fallback order (counting desktops, then phones, by key) that answers on the lease protocol is the fallback arbiter, and a device takes the role itself only after waiting two heartbeats per device ranked before it. Lease tokens never go back across arbiters: every acquire passes the node's own head fence as a floor (`Leases::acquire_above`), and every grant is signed by the arbiter that gave it and carried in the heads written under it (`rowboat_sync::Grant`). A device that sees a live server never follows a fallback grant's head (whatever it holds, nothing included); it does only while it is in fallback itself. The server follows one, whatever its own head, only when the fallback arbiter and the holder were silent to it (gaps in their heartbeats of at least half the takeover delay, from the heartbeat times its lease server keeps across restarts; a full takeover delay for a gap that began before its lease server started, since its own downtime is a gap every device saw), the head's fence lies above its own record's lease, and its record names no other live holder (when it names the server itself, every device must have been silent: a server cut off from all of them). A node that admits a fallback holder's head while it sees the server yields the account (takes and asks for nothing, gives up what it holds) until that holder continues the journal under a grant of the server, or for three takeover delays. The device returns to the server once it answered without a break for the return delay (a quarter of the takeover delay, doubled for each quick return up to eight times), continues what it wrote under the fallback grant under a grant of the server (everyone else treats it as the only node eligible meanwhile), and the server then takes the account back through the usual cooperative handover. A journal a device wrote under a fallback grant that the group did not take (the server kept another device's) is dropped two takeover delays after the server came back. Taking over from a server that went silent (not one that announced leaving), the device presumes every queued command that cannot be repeated started (Skein's `presume_started`), so a send the server may still have run is reported `Uncertain` rather than sent twice. While a device is still in fallback and the server answers its probes again, it announces what it wrote under the fallback grant every tick, so the server yields before its lease server grants again. `Node::announce_leaving` (the server, after handing its accounts back, before `shutdown`) stops arbitrating for good and sends the notice, and returns whether it did: it refuses, and the devices fall back by silence, while the node still leads an account or a worker of one runs (it waits two heartbeats for them first); the next start believes the devices that took over meanwhile.
- **A server node.** `NodeBuilder::class(NodeClass::Server)` builds a node that pairs as a server: `Node::server_invite` returns a server invite (QR, short code, pairing address) and, once a member device adopted it, moves the node record to the device's group and deletes the placeholder group's member key; the node is then rebuilt (as after joining). The server's link answers lease requests, and the adopting device grants it `read` and `lead` on its accounts (question 65 for accounts added later).
- **The headless server's hooks** (`apps/rowboat`, one node per tenant): `Profile::Server` (the desktop's timing, the table only for discovery); `server_invite_confirmed` (the fingerprint also waits for `confirm_pairing` on the server, a console); `genesis_hash` and `adopted` (what a tenant is bound to, and whether a device adopted the node: it then holds no member key, and a later server invite accepts only terms of its own group, so even a server whose peers were all revoked cannot be moved to another group); `lease_holder(account)` (the holder as the arbiter records it, for handing accounts back); `NodeBuilder::signal` (one bus for every node of a host, topics scoped to each group), `push` (subscriptions recorded in the host's push registry), `view_dir` (the mail database elsewhere, rebuilt when empty) and `store` (every object in another store, an S3 prefix, sealed as on disk; the data directory keeps the lock).
- **Who may lead** (the engine's `Eligible`): a node holding `lead` on the account in the group log; this node only while it holds state to continue from (its own record and credentials, or an offer); no other node while this one holds the account's only state (it can lead it alone, the journal's head is unattested or its own, and no peer took an offer since it started). Without the last rule a server adopted before the first sync of a new account was preferred, could not continue and gave every lease back, while the desktop deferred to it, so nobody synced the account (regression: `a_server_adopted_before_the_first_sync_still_takes_the_account`).
- **Revocation notices** (B4). A node every peer refuses asks each, on `peleda/revoked/1`, whether it was revoked, and applies the notice (the log entries up to its revocation) only when it chains from its own head and verifies. On learning it was revoked (or starting revoked) the node stops leading and calls the `NodeBuilder::on_revoked` hook once; wiping is the app's.
- Labels are the profile name (`desktop`, `test`) until the app passes a device name (wave 2).

## Accounts and credentials

`add_account` checks the setup (`rowboat_api::check`, `skein_accounts::admin::check_record`), signs in to IMAP (a session and a mailbox listing) and to SMTP (`Sender::check`) with the password, and only then stores the sealed password (Skein's keyring), the node's account record (`rowboat/accounts/{id}`: address, display name, archive mailbox; `owner` for an account another node leads) and Skein's account record, and wakes the account. Nothing is stored when a sign-in fails. A password enters only through `add_account` and `update_password` and leaves only to the provider being connected; a test scans logs, events, errors, `Debug` output and the objects directory for a canary password.

Removing an account marks it removing and paused at once (it disappears from every read), then, once the engine has let go of it (`Engine::let_go`: a pass over the directory that began after the pause and no worker left, so no sync is mid-way through writing it), deletes Skein's record and password, destroys the account's keyring scope, purges its journal (`Log::purge_account`, which also forgets the head the log saw), commands and control records (`skein_storage::purge_account`), releases a lease this node still holds for it (a worker that ended without releasing, or one from before a crash) and, with the local arbiter, deletes the lease record (`CasLeases::forget`; a lease another node holds stays and is logged), forgets it in the database and deletes the blobs only it named. A removal interrupted by a crash is finished on the next start. What stays is the keyring's tombstone for the destroyed scope (`keys/accounts/{account}`), which keeps a destroyed key destroyed. Blobs the account's journal named but the database never held are not swept.

## The content pipeline and hooks

The node never parses message bytes. `skein-view`'s parser hook is the node's adapter over `Arc<dyn rinse_mail::Content>`: render with display-only options (no original HTML, no remote images, images re-encoded at 1 px, since `max_image_px` 0 made every message with an inline image fail verification), `rinse_mail::verify_rendered` on the result whatever produced it (a failure stores the message as unavailable, with none of the output), map headers, thread facts, text and attachments, then run the spam and category hooks on the same render and store their tags (`spam.junk`, `spam.suspicious`, `category.<id>`). A pipeline that is `Unavailable` leaves the page for the next round. The adapter's version joins its own with the hooks' versions and is stored per message; re-parsing on a version change is not built yet.

## Reads, commands and the overlay

Reads come from `skein-view`: lists newest first with a cursor over `(sort date, account, id)`, so scopes over every account page stably; at most 200 rows. Mutations resolve each target to its memberships and queue one Skein command per account, mailbox and 10,000 items; unknown targets are `skipped`. A pending overlay (at most 10,000 entries, 10 minutes) shows each change at once; an entry is dropped when its commands failed, conflicted or were cancelled, or when they were applied and the database shows the expected state.

`send` composes with `rowboat-compose` (the account's address and name, the node's clock, a ULID `Message-ID`, a random boundary), puts the bytes in the blob store and queues `send` with the account's Sent mailbox (when the database knows one) for the engine, which waits out the undo window. The draft is hidden while the send waits, comes back on `cancel_send` or a failure and is deleted once sent.

## Events

`events()` is a `tokio::sync::broadcast` subscription of 256 events; a subscriber that falls behind gets one `Lagged { missed }` and never holds the node up. Sources: `skein-view`'s observer after each committed page (sync progress, mailboxes, messages, command and send outcomes, and the arrivals `notify.rs` hands to bento's notification policy for `NewMail`, see NODE.md "Notifications"), the status records read every heartbeat (account health), and the node itself (accounts, waiting sends, cancellations).

## Discovery

1. The first source (the table) is asked alone; when it knows the provider, its answer is returned and nothing reaches the network.
2. Otherwise the other sources are asked at once. Candidates from autoconfig and SRV with an IP literal, or STARTTLS on a port other than 143 and 587, are dropped (`Candidate::fit_from_network`).
3. Answers are joined by source rank (table, autoconfig, SRV, guesses) with `rowboat_discover::merge`, so a guess equal to an autoconfig candidate is dropped.
4. With a `Prober`, every candidate not from the table is returned only when both of its servers answered, each distinct server probed once, at most 8 probes in flight; it is marked `verified`. When the servers take no password but offer OAuth the hint becomes `OAuthOnly`; when they take neither, the candidate is dropped. Without a prober (the test profile) such candidates are returned unverified and `add_account` signs in anyway.
5. A candidate not from the table with a server outside the address's domain and outside the table's providers (`TableSource::known_host`) gets `needs_confirmation`, so the app shows it as "suggested by" its source and asks the person.

`ServerProber::new(timeout)` trusts only the web roots; extra roots exist only behind `testing`. Cargo unifies features across the packages of one build, and `rowboat-integration` and `rowboat-load` turn `testing` on, so a release binary is built with `-p <binary>`, never with `--workspace`. `ServerProber` probes with `skein_mail_imap::probe` and `skein_send_smtp::probe` (TLS verified against the web roots, greeting and capabilities, no credential), 10 s per probe, and maps their typed causes to `DiscoverError` kinds (`TlsFailed`, `Insecure`, `Timeout`, `Unreachable`, `NotMail`). Provider errors reach `NodeError` through `MailError::cause()` and `SendError::cause()`, never through their texts.

## Records

`records` holds the node's stored records with versioned decoders (node record, account records, drafts), each fuzzed in `fuzz/`.

## Tests

- `cargo test` (the e2e tests need the `testing` feature, which `rowboat-load` turns on in workspace builds): the API conformance suites on the test profile; first run, sync, threads, search, suggestions and a restart over the same directory; mark-read through the overlay settling with `CommandSettled`; move, archive, delete to the trash and for good; send with the undo window, cancel inside it, send after it, the Sent copy; removing an account and sweeping its blobs and records (only the keyring tombstone stays); a lagging subscriber; attacks: a second process (`Locked`), lost, wrong, short and locked keys (`KeysLost`, `KeystoreLocked`, never a new key), a foreign directory (`NotEmpty`), a refused sign-in storing nothing, targets across accounts, worker output failing `verify_rendered`, and the canary password scan.
- `tests/group.rs`: two and three nodes pairing by QR and joining with a restart, in memory and over iroh on loopback; a revocation that rotates the account's keys, reports the account whose password must change and spreads to the third node; attacks: a wrong secret (which kills the QR invite), an expired invite, a rejected fingerprint, a replayed invite, a node with accounts or with other nodes joining another group; no network means `ServerUnreachable`; a phase 1 directory upgraded once to the group log with its account still usable.
- `tests/replication.rs`: two nodes pair; the owner syncs a fake provider and the second node lists the same account, mailboxes and messages and reads the same raw bytes; a mark-read from the second node shows at once, settles `Applied`, reaches the provider through the owner and comes back through the replicated journal; a send from the second node leaves once, from the owner's sender, settles `Sent` and drops the draft; account management answers `Unavailable`; in memory and over iroh on loopback. Attacks: a forged leaving notice, one signed by a device, and a genuine one replayed while the server answers change nothing; a device that claims the server is silent writes under its own fallback grant but neither the server nor the other desktop follows it, the server keeps the account, and the device drops its journal once it stops claiming; a fallback head replayed after the server took the account back is refused and makes nothing yield. Unit tests (`fallback`): the takeover and return delays, a leaving notice skipping the delay, the doubling return delay for a flapping server, the fallback order without servers and revoked devices, leaving notices from anyone but the group's counting server (or forged, moved, replayed, bit-flipped, oversized, from a revoked server) refused, the server's gap memory, the admission rule, a revoked arbiter's grant refused.
- Load: `tests/load` (`mise run load-node`), including replication to a second node and many accounts handed over to a server at once.
