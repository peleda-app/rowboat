# Decisions

What was decided and why. Decisions of the layers before the merge stay in `baton/docs/DECISIONS.md` and in Skein's history; this file starts with the merge.

## 2026-11-25: the merge (stage 4 of the workspace reorganisation)

Decided by the maintainer:

- **One repository, three layers.** `skein` (this repository's git history, GitHub `peleda-app/skein`), `baton` (no commits) and `smereka` (documents only) become `rowboat`, Peleda's node. `baton/` is coordination, `skein/` the mail engine, `crates/` and `apps/` the node (empty for now).
- **Public, PolyForm Noncommercial 1.0.0.** Commercial use needs a license from the maintainer; contributions need the signed CLA (`CLA.md`, synced from dojo).
- **Names.** Crates keep `skein-*` and `baton-*`; the node's own crates will be `rowboat-*`.
- **No web interface, no HTTP management API.** The web portal, the TypeScript client, `openapi.json`, the HTTP management API of `skein-server`, and the HTTP server and HTTP follower of `skein-view` go away. A minimal inbound endpoint stays for Gmail Pub/Sub and Microsoft Graph change notifications (`skein-push`, with their authenticity checks) and a health check. The node is managed through Baton commands from the app, later.
- **The rule against describing the mesh is gone.** Skein's local note that Skein is the open part and must not describe the mesh, device nodes, pairing, the relay or the hosted node no longer applies and was removed; the rest of that note stays, in `AGENTS.local.md` at the root and in `skein/`.
- **Uncommitted work moves along.** Skein's 153 uncommitted changes (the switch to Baton contracts) were moved into `skein/` uncommitted, byte for byte apart from the edits listed below.

Taken without the maintainer, with reasons:

- **Plain moves, two workspaces for now.** Every Skein file at the root moved into `skein/` with `mv` (git sees the renames once staged); Baton was copied into `baton/` without `.git` and build output; `../baton` and `../smereka` stay on disk untouched. `skein/Cargo.toml`'s `../baton/crates/...` paths now resolve inside the repository, so neither layer's build changed. One workspace and one `Cargo.lock` are a separate next step (reconciling `hmac` and `sha2` versions and the rustls crypto provider), so that the move itself changes nothing that compiles.
- **Root `mise run check`** runs `mise run check` in `baton/`, then in `skein/` (both unchanged), then `dojo check .` through `../dojo`, as `rinse` does.
- **`dojo.toml` excuses `LIC-PUBLISH` for `skein` and `baton`.** Every member inherits `publish = false` from its layer's `[workspace.package]` (or sets it), but with no root `Cargo.toml` dojo resolves `publish.workspace = true` only against the repository root and reports all 71 members. The two entries go away when the layers become one workspace.
- **License files.** No full PolyForm text is on this machine and none may be downloaded, so `LICENSE.md` names the license, gives its official URL (the license allows giving recipients the URL instead of a copy) and the Required Notice "Copyright 2026 the rowboat authors"; the licensor's name and the full text are a question for the maintainer. Cargo `license` is `PolyForm-Noncommercial-1.0.0` in both layers' `[workspace.package]` and both fuzz manifests; `publish = false` is set in both workspaces and every member inherits it (`publish.workspace = true` was added where it was missing); `documentation` links to docs.rs were dropped and the `repository` and `homepage` fields point at `peleda-app/rowboat`. The four `package.json` files carry the same license; `openapi.json` and its source say so too until they are removed.
- **Publishing removed.** `release.yml` and `skein/release-plz.toml` existed only to publish crates to crates.io and the client to npm and were deleted; the npm job left `publish.yml`, and `packages/client/scripts/prepare-publish.ts` and the client's `publishConfig` went with it. `publish.yml` keeps the signed, attested container images and binary archives, built from a tag `vX.Y.Z` pushed by the maintainer (it runs only in `peleda-app/rowboat` and only with `RELEASES_ENABLED`). `skein/docs/RELEASING.md` describes it.
- **Images are named rowboat.** `ghcr.io/peleda-app/rowboat` (with `-headless` tags) and `ghcr.io/peleda-app/rowboat-view`; archives are `rowboat-vX.Y.Z-<target>`. The binaries inside keep their crate names (`skein`, `skein-view`) until the node layer has its own binary.
- **Docker builds use the repository root as context.** `skein/Dockerfile` and `skein/apps/view/Dockerfile` copy `baton/` and `skein/` and build in `skein/`; the root `.dockerignore` replaces Skein's.
- **Workflows at the root run per layer.** CI's `check` job checks out the repository at `rowboat` and dojo beside it and runs the root `mise run check`; integration, load and live run in `skein/`; the image job builds all three images from the root; `cargo deny` and the fuzz workflow run once per layer (Baton gained a fuzz job it did not have). The `pre-push` hook in `.git/hooks` stays: it blocks pushes until the GitHub repository is renamed.
- **Docs site and links.** The site's base moved from `/skein` to `/rowboat` (GitHub Pages of the renamed repository) with every internal link; GitHub links point at `peleda-app/rowboat/blob/main/skein/...`. The site still documents the HTTP API until the removal reaches it.
- **`deny.toml`** at the root and in both layers is dojo's template. The layers' old copies lacked `[licenses.private] ignore = true`, so `cargo deny` would have refused the repository's own `PolyForm-Noncommercial-1.0.0` crates; with `publish = false` they count as private and are skipped. CI runs `cargo deny` per layer until the workspaces are unified. `cargo-deny` is not installed on the machine that made this change, so this was not run locally.
- **The app** points `baton-seal` at `../rowboat/baton/crates/seal`, checks out `peleda-app/rowboat` in CI and mounts `../rowboat` in its Linux container; `bento` and `peleda-insight` have no path dependencies on Skein or Baton and were not changed.
- **dojo's registry** lists `rowboat` as `active` and `skein`, `baton` and `smereka` as `retired`.

Taken without the maintainer, with reasons:

The lock was seeded from both layers' locks so no dependency moved to a version neither layer had tested; where the two locks disagreed the newer one was kept (`hyper` 1.13.0, `zerocopy` 0.8.65). Lints were already identical; Baton's `opt-level = 3` dev overrides for `argon2` and `blake2` are kept.
- **One `hmac` and one `sha2`: 0.13 and 0.11.** Baton's only direct use of `hmac` 0.12 and `sha2` 0.10 was the invite proof in `baton-identity` (HMAC-SHA256), which needs neither version: `ed25519-dalek` uses `sha2` 0.10 internally and still does, transitively. `baton-identity` moved to the workspace entries (one import of `KeyInit` added); HMAC-SHA256 output is the same in both versions and its 11 tests pass. `baton-seal` and `baton-keys` dropped the `sha2-v0-11` alias for plain `sha2`. No second key was needed.
- **aws-lc-rs is the only rustls crypto provider.** Baton needs it for the hybrid post-quantum `X25519MLKEM768` group that `baton-link-iroh` requires. Skein's `tokio-rustls` entry switched from `ring` to `aws_lc_rs` (keeping `tls12` and `logging`), `rcgen` uses Baton's `aws_lc_rs` and `pem` features without defaults (its default turns on `ring`), and the three places that picked `ring` explicitly (`skein-core`'s test TLS acceptor, `skein-mail-imap`, `skein-send-smtp`) pick `aws_lc_rs`; `jsonwebtoken`, `reqwest` 0.13 (`rustls`) and `iroh` already used aws-lc-rs. `cargo tree -e features -i ring --target all --all-features` prints nothing, so `ring` is never compiled; it stays in `Cargo.lock` only as an optional dependency of `rustls-webpki` and `quinn-proto`. Every TLS configuration in the repository names its provider (`builder_with_provider`), and with a single provider compiled rustls' process default cannot be ambiguous, so no process installs a default. `baton-link-iroh`'s tests that check the negotiated group and refuse classical-only peers pass in the workspace.
- **Feature unions.** `axum` takes Skein's defaults (Baton had `http1` and `tokio` only; the defaults add `json`, `query`, `form`, `matched-path`, `original-uri`, `tower-log` and `tracing`); `hyper` adds `http2` and `hyper-util` adds `server-auto` for Baton; `reqwest` adds `socks` and `stream` for Baton's `baton-mailbox-drop`; `tokio-rustls` adds `logging`; `tracing-subscriber` takes Skein's defaults plus `env-filter` and `json` (Baton had no defaults). The last change would turn on ANSI colours and the `log` bridge in Baton's binaries, so `batond` and `drop` now call `.with_ansi(false)` and print as before; the `log` bridge means records of dependencies that log through `log` reach their INFO output. Baton's log test (no box ids, keys or addresses at TRACE) passes with the union.
- **One `mise run check`.** It runs everything both layers' checks ran (Baton's unsafe scan, fmt, clippy and tests over the workspace, Skein's `otel` and `portal` feature builds and the bun checks), plus `cargo fmt --check` and `cargo check --bins` on stable for both fuzz workspaces as dojo's template does, then `dojo check`. The fuzz crates' targets were reformatted once with `cargo fmt` (layout only) and set `[lints.rust] unsafe_code = "forbid"`, which dojo requires of crates outside the workspace.
- **Fuzz workspaces stay per layer.** Each keeps its pinned nightly, corpora, lockfile and `run.sh`; merging them would move Skein's uncommitted targets and corpora and every fuzz path in CI and docs for no gain. `dojo.toml` excuses `TEST-FUZZ` at `fuzz` for that reason, and the two `LIC-PUBLISH` exceptions are gone since every member now inherits `publish = false` from the root.

The Dockerfiles copy the root `Cargo.toml`, `Cargo.lock` and `rust-toolchain.toml` with both layers and build in `/src`; `publish.yml` reads the version from the root `Cargo.toml` and builds the archives from the root.
- **`skein`'s `anyhow` dev-dependency** now uses the workspace entry (dojo `MOD-WORKSPACE-DEPS`).

## 2026-11-25: the portal and the HTTP management API removed

Carried out as the maintainer decided (see the merge section): the portal, its feature, `rust-embed` and Docker stage, the bun steps, `@peleda-app/skein-client`, `openapi.json` and `utoipa`, the management routes of `skein-server` with their auth machinery, the docs site's API reference, and `skein-view`'s binary, HTTP API, HTTP follower and image are deleted.

Taken without the maintainer, with reasons:

- **`skein-server` keeps its name and becomes the inbound listener.** It serves `GET /v1/health` and the Gmail and Graph push routes, nothing else (every other path is 404). The `/v1` prefix stays on these paths because Graph subscriptions and Pub/Sub push subscriptions are registered with them. `router(signal, push, &config)` replaces `router` and `router_with_push`.
- **A push rate limit was added.** The task asked to keep the push receivers' rate limits, but they had none: the per-key limiter belonged to the management API. One token bucket per receiver (`push_rate_per_second`, default 100, 429 with `Retry-After: 1`, which both providers retry) bounds the storage reads a flood can cause; health is not limited. Review on the same day: a single bucket in front of authentication let forged requests starve genuine pushes, so Gmail spends its token only after the path secret matches and Graph has its own bucket; a Graph flood can still delay Graph pushes (they fall back to polling), since Graph has no secret before the body is read. Body limits (64 KiB), the 30 s body idle timeout, the header timeout and the connection cap stay.
- **The metrics listener stays, on loopback only.** It is observability, not management, and serves only `/metrics`; the inbound listener serves only push and health. Review on the same day: the maintainer allowed only push and health inbound, so `metrics.listen` must be a loopback address (anything else fails `check-config`), metrics leave the host only through OTLP, and whether to drop the listener altogether is question 21.
- **Management moved to the binary's subcommands** (`skein tenant`, `account`, `journal`, `webhook`, `push-token`), which open the node's storage and master key file and write through the same stores. Secrets come from stdin. The checks the routes ran moved into libraries so Baton commands can reuse them: `skein_engine::{check_command, submit_command, cancel_command}` and `skein_accounts::admin` (record, password, send key and token checks, tenant register, unregister and purge, account deletion). A command queued from the command line is hinted only in its own process, so the owner picks it up on its next round (at most `engine.interval_secs`).
- **Dropped with the API, not ported:** API keys, scopes, IP allowlists, trusted proxies, the per-key rate limits and stream caps, CORS, the account host policy (`account_hosts`: only the operator writes records now), OAuth sign-in through the server and its callback and pending sign-ins (the app will sign in and hand tokens over; `skein account grant` does it today), webhook test pings, and `traceparent` from request headers. `[server.webhooks]` moved to `[webhooks]`; OAuth clients no longer need `redirect_url`. The removed config keys are refused, so an old config fails loudly.
- **Outgoing webhooks stay.** `skein-webhooks` never depended on the API; its endpoints are managed with `skein webhook`. Whether Peleda needs them is question 17.
- **`skein-sse` stays**: `skein-mail-jmap` uses it for JMAP push.
- **`skein-view` became a library in `skein/crates/view`**, following a tenant's journals straight from the storage contracts: heads checked with a `HeadAttestor`, segments read through `Chain` and checked with `verify_segment` like the tiered storage does with untrusted tiers, the last fully applied segment stored (schema version 3) so a rolled-back head or swapped history is refused, compaction answered with the latest snapshot. It wakes on the engine's `heads/{account}` signal hints when given a signal. Its query API is the `Store` the HTTP API used, with every list capped at 1000 rows; the app will embed it.
- **Tests ported, not dropped:** command checks and cancelling (to `skein-engine`), record, SES and secret checks, sealing and purge (to `skein-accounts`), the listener, header, body and push tests (kept in `skein-server`), every `skein-view` end-to-end scenario (to the library, plus attack tests), the binary end-to-end scenario (to the subcommands, in `binary.rs` and the new `apps/skein/tests/cli.rs`). Deleted because they tested the removed API itself: key auth, scopes, admin routes, cross-tenant key walks over `openapi.json`, IP allowlists and trusted proxies, rate limits and stream caps per key, CORS, the account host policy, the OAuth start and callback flow, event paging and 410, blob ETags, the SSE stream, webhook routes and test pings, the OpenAPI drift and operation id tests, the portal's file serving, view's REST routes, token auth and CORS, and the HTTP request-parsing property tests (the path and label properties are ported to `skein-engine`). The load tests never used HTTP.
- **Images.** One image, `rowboat`; the `-headless` variant and `rowboat-view` are gone (question 15 resolved). The docs site keeps its own `bun.lock`, pruned by hand of `starlight-openapi` and the 74 packages only it pulled in, since no download was allowed.

## 2026-11-25: review of the restructuring

Taken without the maintainer, with reasons:

- **Push rate limits after authentication.** Gmail spends its token only after the path secret matches, and Graph has its own bucket, so forged requests cannot starve genuine Gmail pushes (test: a flood of wrong-secret and Graph requests, then a genuine Gmail push still answers 204). A Graph flood can still delay Graph pushes; question 20.
- **`skein-view` rebuilds only forward.** A missing segment was taken as compaction and the latest snapshot replaced the account's state, checkpoint and tip whatever its `seq`, so whoever could write storage could roll a follower back or past the head. A snapshot at or before the checkpoint is now `Rollback` and one past the attested head is `Mismatch`, with nothing changed (two attack tests). Binding snapshots to the chain is question 19.
- **`metrics.listen` must be loopback.** Only push and health may listen beyond the host; question 21 asks whether to drop the listener.
- **`skein journal get-blob` writes a new owner-only file** (mode 0600, `create_new`, so an existing path or symlink is refused), like `skein export`.
- **Secrets are never typed into a terminal.** The commands that read secrets from stdin refuse a terminal and ask for a pipe or file, rather than echoing the secret; no new dependency was added for hidden input.
- **`baton/mise.toml` deleted**, as the restructuring entry above already stated; `mise run check` from `baton/` now runs the root check.

- **Known deviations from MOD-1 and MOD-2, labels kept.** `skein-storage` is labelled `contract` but is not only one: beside its traits, types and suite it holds implementations of its own traits on top of `Objects` (`ObjectLog`, `ObjectControl`, `ObjectCommands`, `ObjectBlobs`, `CountingObjects`) and `ControlState`, an adapter onto `baton-state`'s `StateStore`. `contract` is closer to the truth than `library`, which would only dodge the suite check; the honest fix is a split (question 22). Baton's `fuzz/corpus` is gitignored, so the `keys_box` seed lives in the tracked `baton/fuzz/seed-corpus/keys_box`, listed in `baton/fuzz/seeds`.

## 2026-11-26: license keys

Decided by the maintainer:

- **rowboat stays public under PolyForm Noncommercial 1.0.0**, free for personal use and noncommercial organizations with no key.
- **Three additional licenses granted by Peleda**, automatically where possible: a free Small Team License (any purpose, up to 5 users counted with affiliates, no service to third parties, issued after a confirmed address and accepted terms); a free Organization License (human-rights organizations, press freedom and investigative journalism, legal aid, digital rights, refugee aid; by application, decided by the maintainer, one year, renewable, revocable on stated grounds; not governments); a paid Commercial License (companies above 5 users and hosting providers, through hallway's merchants of record).
- **A key is a signed certificate, not a lock**: verified offline against embedded public keys, shown in the app, never phoning home, no telemetry, never blocking anything; honest notices only. Revocation by one-year expiry and a list shipped with updates, never fetched behind the user's back. Licensees screened against sanctions lists with the sanctions repository; licensee data minimal.
- **The plan includes the implementation of the keys** (format, hierarchy, ceremony, rotation, compromise, verifier): [LICENSING.md](LICENSING.md).

Taken without the maintainer, with reasons (from three independent designs, judged field by field; the security-first design is the base):

- **Format.** Postcard `{ version, body, signature }` with a versioned body and `context || 0x00 || body` framing, as hallway's signed statements and Baton's `sign(context, message)` do, Ed25519 with `verify_strict`, sizes checked before signatures, and a canonical rule (decode, re-encode, compare) so no second spelling of a certificate exists. JSON, JWT and X.509 were rejected for their parser surface and non-canonical forms. No extensions field: a new field is a new version.
- **Roles per issuing key.** Separate Small Team, Commercial, Organization and revocation keys under two offline roots, so a leak of the online Small Team key can mint only Small Team certificates and no online key can sign revocations. One shared automatic key (one of the designs) was simpler but widened the blast radius for little saving.
- **Verify ignores the clock; status uses a monotonic floor.** A wrong clock changes what is shown, never what is accepted; rollback cannot revive a license past times the node has seen.
- **Sticky revocations instead of an unbounded union.** The node keeps the newest list plus every revocation it has seen for its installed certificates, issuers and roots, so a leaked revocation key cannot revive anything while the issuer can drop long-expired serials.
- **Scope as a bitset with unknown bits invalid**, adding `SERVICE_TO_BENEFICIARIES` for the Organization License: the right the base license and Small Team lack, and the main reason a registered charity would want the license.
- **Holder keys optional.** A key requested from the app carries the owners' Baton member keys (proof of possession), which shows a copied certificate as not bound; a key requested on the web carries none. Binding never blocks.
- **Text outside the armor is ignored and never shown**, rather than human headers that must match the body: readable files with a smaller parser.
- **Two crates in rowboat:** `rowboat-license` (pure, no Baton dependency, so hallway can depend on it by path under LIC-5 without pulling in Baton) and `rowboat-licensing` (service crate over `StateStore` and `GroupState`, no network crates). Format and vectors in one place, so issuer and verifier cannot drift.
- **Users are member keys with a live, non-blind node certificate**, deduplicated across the groups a node serves; shown as "about N"; the contract's definition governs.
- **Notices only for owners and admins, only in Settings, dismissible for 90 days, no operating-system notifications**; none ever for a group without a certificate on a phone or desktop. Renewal reminders come by mail from the issuer.
- **Phases are named L0 to L9** so they do not collide with the repositories' own numbering; L1 starts now since it does not need the node layer.
- **Question 12 is resolved** by this decision; the README's license section names the three licenses and the placeholder URL `https://peleda.app/license`. New questions 24 to 37.

## 2026-11-26: license plan revised after review

Taken without the maintainer, with reasons (review findings on [LICENSING.md](LICENSING.md)):

- **Revocation cannot be frozen by one stolen revocation key.** Two distinct revocation keys A and B on separate tokens, both pinned by every release; list numbers may grow by at most 2^20 per list; a list naming the stored list's signer in `issuers` replaces it whatever its number; a release resets a list whose signer it no longer pins or that its embedded list revokes; a list's `issued_at` must lie in its key's window; sticky entries remember their signer and go when it is revoked. The Organization issuer moves to its own token (O), so one theft plus one PIN breaks one role.
- **Dates bounded by the delegation.** `not_before <= issued_at + 31 days` and `not_after <= issuer.not_after + max_license_days`, so a leaked or retired issuing key cannot mint certificates for later years; old seeds are destroyed 30 days after the switch. Kind caps (365 days for Small Team and Organization, 400 for Commercial) are separate from the issuer cap, so the Organization issuer (400) can sign hand-made Commercial deals with grace. Windows: 15 months for issuing keys, 25 for revocation keys.
- **Lists fit a Baton command.** `MAX_REVOCATIONS` is 48 KiB (2 500 serials, 64 keys, 8 roots, all sorted and unique) so `license-revocations` stays under Baton's 64 KiB `MAX_ENCODED`; armored lists have their own 72 KiB limit. Deltas or peer fetch are question 38.
- **Server licenses belong to the operator.** On the server profile only the configured operator key (or the owners of the operator group) manage the license and see counts and notices; hosted groups see that the operator manages it, nothing else.
- **Holder keys are licensing-only keys, binding is opt-in.** The app creates them; the link to a member exists only on the node (`holder_proof` at install). Certificates no longer carry Baton member keys.
- **`ServiceWithoutLicense` only with an installed certificate.** With no key installed no notice ever appears.
- **The clock floor is recomputed from signed values**, with the observed clock capped at signed values plus 35 days and resettable by owners (`license-reset-clock-floor`), and cleared when no certificate is installed.
- **Requests reach the page in the URL fragment or as a file**, never in a query string; single use; a leaked request locks nobody out because the app makes new holder keys.
- **Versions down the chain**: every object's wire version is at least its signer's `min_version`.
- **Display names**: Unicode categories Cc, Cf, Co, Cn, Zl, Zp refused; Small Team certificates carry no name (nobody checks it); Commercial names are checked against the payment record.
- **One renewal window**: requested from 60 days before the end, `not_before = max(issued_at, old not_after − 30 days)`.
- **L5 split** into L5a (device and app, part of the go-live gate) and L5b (server, with phase 3).
- **"Reissue" means a new serial**; downloading the same certificate again is "download".

## 2026-11-26: node phases 0 and 1 built

Taken without the maintainer while building [NODE.md](NODE.md), with reasons:

- **`rowboat-node` is a `library` in dojo's terms although it is a composition root** (a node builder, MOD-4): dojo has no kind for a composition library, as for the app's `peleda-core`. It depends on implementations (`skein-storage-fs`, `skein-storage-sealed`, the IMAP and SMTP providers, Baton's CAS leases, the hooks) and picks them per profile.
- **The test profile keeps sealed file storage** instead of memory objects, so restart and lock tests run over the same directory; it differs from the desktop only in its providers and timing.
- **`skein-view`'s parser hook returns the existing `Parsed`** (now with `tags`) instead of a new `ParsedMessage` type: the fields are the same and the default `mail-parser` path keeps working unchanged. ## 2026-11-26: file storage shared between the server and its subcommands

Taken autonomously to fix two CI failures of commit `cc7ecd7`.

- **One owner, shared handles, a lock per write.** `skein-storage-fs` held an exclusive lock on `<root>/.lock` for the life of every handle, so with the HTTP management API gone (2026-11-25) a running `skein serve` could not be managed at all: every subcommand failed with "in use by another process". Now `FsObjects::open` (the server, the node, the load tests) still takes that lock as the directory's owner, so a second server is refused, and `FsObjects::open_shared` (the subcommands, export, import, copy) takes none. Every `put` and `delete`, from either kind of handle, holds an exclusive advisory lock (`flock`, `LockFileEx`) on one of 64 stripe files under `<root>/.locks` for its read-compare-write; writes stay atomic by rename and reads stay lock-free.
- **Why this is enough.** Every store above `Objects` (control records, journal heads and segments, blobs, the command queue, Baton's lease records) is made of compare-and-swap, so cross-process compare-and-swap keeps every guarantee they had: appends stay fenced, commands are created with `Expect::Absent`, two writers of a key see one success. Multi-process tests (children of the test binary) fail without the stripe locks and pass with them. Stripes are chosen by FNV-1a, not the standard hasher, so every process and build agrees.
- **No wake across processes.** The engine already re-reads tenants and accounts every heartbeat and an account's queue every round, so a command submitted from the command line runs within `engine.interval_secs`, which the integration test's deadlines allow. A hint file or a cross-process signal was left out until that latency matters; the node will take Baton commands anyway.
- **The node layer keeps its exclusive open.** `rowboat-node` calls `FsObjects::open`, whose meaning (owner, refused while another owner runs) did not change.
- **Linearity of group verification is counted, not timed.** `verifying_a_long_log_stays_linear` asserted under 20 s of wall time and failed on a slow runner (TEST-3 forbids wall-clock assertions). In test builds `baton-group` counts units of work per thread (one per applied entry, one per resource state copied); the test requires the work for 3,000 entries to be at most three times the work for 1,000 plus a constant. A state copy per entry, the quadratic shape it guards against, makes the ratio about nine and fails it. The timing check stays in the `group` load scenario, which already has an explicit budget.

## 2026-11-26: wave 1, part 2 built (replication and commands)

- **S1 as two calls, `Log::stage` and `Log::install`.** GROUP.md had one call taking the head and every segment; a replica far behind would hold the whole gap in memory. Staging writes each verified segment ahead of the head, invisible to reads (a segment counts only once a head covers it), and `install` then walks the chain locally from the new head to the local tip and moves the head with the owner's attestation verbatim. Memory is bounded by one segment, a catch-up resumes after a crash from what is staged, and staged segments that end up off the chain are removed by the install that passes them. `TieredLog` and the Skein load suite's recording log delegate.
- **Segments travel through `baton-fetch` with a locator** (Baton B5, a generic change): the content id is the segment's hash as GROUP.md says, and the segment's name rides along so the serving node reads it by key instead of searching by hash. `PeerTier` is a Skein `ReadTier` over it (S2), and the node's storage is `skein-storage-tiered` over its local storage with that tier, so blobs the view or `message_raw` lack come from peers too.
- **Head announcements over a link protocol, not signals.** The node has no mesh yet (B2 for the mesh is not built), so an owner pushes its new heads on the link protocol `head` (`Announce`), and readers ask for heads on the same protocol (`Ask`) at start and every 5 minutes. The head is the same signed value GROUP.md describes; moving it to `baton-signal-mesh` later changes only the carrier.
- **Two attestation checks.** `NodeAttestor` (Skein's attestor for the node's own storage) signs every head with the node key and, reading its own storage, accepts unattested heads (journals from phase 1 until their next append) and heads signed by any node the log ever certified (so a revoked owner's history stays readable); `verify_remote` is the strict check every head from a peer passes first (attested, signer counts now and holds `lead`). Skein's `head_attestor` suite refuses unattested heads, so `NodeAttestor` does not run it; its own tests cover signing, other heads, flipped bytes, unknown signers, another context and other versions.
- **Blobs before the head.** A replica fetches the blobs of the events it staged before installing the head, so `skein-view` never parses a message whose bytes are not here (it would store it as unavailable for good). Missing blobs hold the head back for up to three catch-ups; after that the head is installed anyway and the messages read as unavailable. Peers serve a blob for an account only when their view holds a message or object of that account with it, or a command they issued names it.
- **The owner is whoever signed the newest verified head.** Wave 1 has no lease across nodes; a reader learns the owner from the attestation, and the owner describes the account (address, display name, archive mailbox) in its head answers. The reader keeps an account record with `owner` set, so every read path of phase 1 serves the replica unchanged; health stays `unknown` (status records are not replicated yet).
- **Remote commands carry Skein commands, not `rowboat-api` requests.** The issuer's overlay, `CommandSettled` and `SendSettled` are keyed by the Skein command id the journal names, so the issuer must know the id the owner queues. The payload (`RemoteRequest`) is a Skein command for flags, move, delete and send, a cancel or a sync; its id is derived from the issuer, the resource and the idempotency key (a ULID: its timestamp and 80 bits of a keyed hash), so both sides compute it, two issuers never collide (the same key from two issuers makes two commands) and an issuer cannot use another's id (`wrong_id`). The owner checks what a local call would: the class matches, Skein's `check_command`, the account and, for a send, the envelope's sender is the account's address. The composed message is fetched by the owner from the issuer (blobs of outbox commands are served to the account's readers).
- **`cmdkey` records keyed by queue id**, at `rowboat/cmdkeys/{account}/{queue id}`: since the queue id already binds issuer, resource and key, it replaces GROUP.md's hash of the three. States `claimed` (written put-if-absent before queueing), `queued` and `refused`; a redelivery of a `claimed` command that is not in the queue is queued again when repeatable (flags) and answered `Uncertain` otherwise, so a send never runs twice. Records are pruned after two days.
- **`Applied` means queued.** The execution's outcome (applied, failed, sent, uncertain) reaches the issuer through the replicated journal, as for a local command; the Baton result only settles what never reaches the queue (a refusal, an expiry, an uncertain claim). A refusal before a command opens (bad signature, wrong group, expired, not authorized) is a plain reason over the authenticated link rather than a signed result, because `CommandResult::sign` needs a checked command; the issuer believes it only from the peer it believes leads the account.
- **The outbox is rowboat's, mesh-and-link only.** B3 (Baton's generic outbox with mailbox delivery) is not built; `rowboat-sync` keeps a durable outbox in the control store (at most 10,000 commands) and delivers over the link only, retrying every tick while the owner is reachable. A command to an owner that stays offline expires after 24 hours and settles `Failed { expired }`. It moves to B3 when B3 lands.
- **Account management stays on the owner.** `update_password`, `update_account` and `remove_account` on a followed account answer `Unavailable`; drafts stay local; `cancel_send` on a followed account is reported `Cancelled` at once (an owner that already started the send settles it through the journal later). `outbox()` lists only the node's own queue, not remote sends waiting in the replication outbox.
- **Replication timing.** The desktop checks the heads of the accounts it leads every 2 s and announces changes, and asks its peers every 5 minutes; the test profile does both every follower poll. Commands are delivered at once and retried every tick.
- **No S3 tier and no refetch through the owner yet.** The node has no object storage configured in wave 1 (the `storage` resource and its credentials are wave 2), so the tiered storage holds only the peer tier; a blob no peer has stays unavailable. `mail-refetch` as a remote request (the owner asks the provider again, then serves the blob) waits for the app to ask for it; `RemoteRequest` grows a variant then.

## 2026-11-26: review of wave 1 (server authority, hostile peers, commands)

- **A server holds no member authority** (a generic Baton change). A `server` node is certified under its member key, but `baton-group` no longer lets it act as its member: it cannot add or remove members, certify or renew nodes, create resources or revoke any node but itself, and grants to its member (`Principal::Member`) do not reach it; it holds only the grants that name it (`Principal::Node`). This is the class filter Baton SECURITY.md describes, fixed for servers: "the member's desktops and phones". Before, an adopted server inherited the owner's role and every account's admin and command classes, and could add an owner it controlled.
- **An adopted server gets read and lead on the chosen accounts, nothing else.** `Membership::grant_server` grants `Principal::Node(server)` read and lead on each resource and shares only those epochs; pairing calls it with `Certifier::server_grants`. Until the app's picker (wave 2) the node passes every account and `storage` resource its member created, the person's whole setup; accounts added later are not granted automatically (question 65). No command class reaches a server: commands are for the person's devices.
- **The group log exchange verifies as it reads.** Each entry is applied to a working copy of the log as it arrives and the stream is dropped at the first that fails; a batch carries at most 4,096 entries and 16 MiB (the sender stops earlier, always sending at least one entry). A candidate in pairing verifies the welcome log the same way and takes at most 100,000 entries and 64 MiB.
- **Pairing attempts.** Only a valid PAKE message followed by a failed key confirmation counts against an invite; an invalid point releases the reservation untouched. An unauthenticated joiner has 10 s per handshake message (the joiner's software answers, nobody is asked), a failed handshake keeps its slot one more second, a stream waits at most 10 s for one of the two slots, and the node serves the streams of a pairing endpoint concurrently (at most 8 waiting or served). The short code keeps its 10-bit id (GROUP.md's two characters); per-address limits are question 66.
- **A remote cancel names the issuer's own send.** The owner cancels only a command whose `cmdkey` record names the cancelling node as issuer, is `queued`, and is a send still in the queue; anything else is `not_queued`, so a node with `mail-send-cancel` cannot cancel another node's or the owner's sends.
- **`mail-delete-forever` is its own class**, as GROUP.md says: `delete(.., permanent: true)` and a remote `Delete { to_trash: false }` need it, delete to the trash needs `mail-delete`. The other class names stay as built (`mail-sync`, `mail-draft`; no `mail-refetch` until `RemoteRequest` carries it) rather than GROUP.md's `mail-sync-now` and `mail-draft-save`; nothing outside this repository uses them yet, so GROUP.md now lists the built names. Groups created before this change lack the class until their resources are granted again (none shipped).
- **A send's blob is fetched after the answer.** The owner answers `Later` at once, records `fetching` and fetches the blob in the background; when it arrives the owner queues the send itself, and the issuer's next delivery finds it `queued`. A failed or slow fetch is transient (the next delivery tries again until the command expires), never `blob_missing`. A redelivery while the first run is under way answers `Later` instead of `Uncertain`. `baton-fetch` grew `min_rate` (a generic change): an object of `n` bytes gets `n / min_rate` seconds on top of `peer_timeout` on both sides; the node uses 64 KiB/s, so a 64 MiB message has about 17 minutes.
- **An owner behind on the group log asks to catch up.** A command sealed under a key epoch the owner does not know yet is answered `Later`, and the owner exchanges logs with the issuer at once (`Host::group_behind`), so a command issued right after a revocation's rotation is not lost. A `Refused` reason is already checked to be one word when the frame decodes, so it reaches the app filtered.
- **Fuzz targets for the fetch request and the segment locator**: `baton-fuzz`'s `fetch_request` (`baton_fetch::fuzz_decoders`) and `rowboat_sync::fuzz_locator` in `sync_wire`.

## 2026-11-26: two node tests that failed under load

- **An invite's endpoint answers until its timer, its cancellation or its use.** The node's invite server checked `is_pending` before accepting the first stream, so an invite whose clock time had passed before the spawned server first ran closed its endpoint without a word and the joiner saw `ServerUnreachable` instead of `AuthFailed`. Under the load of `mise run check` the server task was scheduled after the test advanced its manual clock (`a_tampered_or_expired_invite_is_refused`). The server now accepts until the endpoint closes (the real-time time-to-live, `cancel_invite`) and checks `is_pending` only after a stream finishes; the handshake refuses an expired invite as before. Regression: `an_invite_expired_before_its_server_first_runs_still_answers`, on a current-thread runtime where the race always happens.
- **Removing an account waits for the engine, not a grace period.** The removal slept a fixed `removal_grace` (25 s on the desktop, 150 ms in tests) and then purged. A worker still inside a session kept its lease, so `CasLeases::forget` left the lease record behind for good, and a sync still writing could put objects back after the purge (`removing_an_account_sweeps_its_mail`). Skein's engine now has `Engine::let_go(tenant, account)`: it resolves once `run` has finished a directory pass that began after the call and has no worker for the account left, its lease released (or once `run` has returned). The node keeps a clone of its engine, waits on it before `remove_now`, and releases a lease it still holds itself (a worker that ended on its own, or one from before a crash) before forgetting the record. `removal_grace` is gone from `TestTiming` and the desktop timing. Regressions: `letting_go_waits_for_a_busy_worker_and_its_release` (skein-engine) and `a_removal_waits_for_the_engine_to_let_go_of_the_account` (node), both catching the worker inside a session with the new `FakeMail::hold`. The node test sleeps 300 ms while the worker is held: on the old code that let the grace pass, so the test failed every time; on the new code its result does not depend on that sleep.
- **Tests of `rowboat-group`, `rowboat-sync` and the node wait on events, not deadlines.** Polling loops bounded by a number of 10 ms tries (2 s to 5 s of wall time), `tokio::time::timeout` of 5 s to 20 s around steps that must succeed, the node tests' 20 s `until`, and a `started.elapsed() < limit` assertion are replaced by unbounded waits under a 300 s hang detector (`within`, `until`, `eventually`), whose only job is to end a test that would never finish. Step limits that only a hostile peer should reach (pairing `step`, `handshake`, `confirm`; the group log and replication `limit` and fetch `peer_timeout`) are 300 s in those tests; tests that expect a timeout run on a paused clock with their own short limit, as before. "The answer did not wait for the blob" is now checked as `fetching() == 1` right after the answer, while the stalled fetch can only end through the test. The test profile's pairing limits are 300 s for steps, handshakes and confirmations, with no pacing of failed handshakes: `a_silent_peer_on_the_pairing_endpoint_does_not_hold_up_the_joiner` failed under six parallel copies of the node suites because the silent stream's 10 s handshake deadline passed before the loaded test reached its check, and the 1 s pacing sleep held one of the two handshake slots on real time. Both deadlines stay tested on a paused clock in `rowboat-group`. Quick negative checks ("no notification within 1 s") stay: they can only miss a stray event, never fail a correct node, and the positive wait after each checks that the next notification is exactly the expected one.
- **The undo window test no longer races the wall clock.** `send_with_an_undo_window` cancelled sends inside a 1.5 s undo window measured by Skein's real clock; under heavy load the window passed before a cancel and the send was gone (`NotFound`). It now runs with a one-hour window (cancel, cancel again, nothing delivered), and the delivery, the stripped `Bcc` and the sent copy moved to `a_send_leaves_without_its_bcc_and_files_a_sent_copy` with no window. The window's end is Skein's send scheduling and stays tested there.
- **Shutdown frees the data directory for certain** (seen as `Locked` on reopen under eight parallel copies of the node suites). `Node::shutdown` waited at most 30 s per task and left a slower task running, aborted the group's tasks without waiting for them, and never touched tasks spawned outside its list (wakes, removals, catch-ups, announcements, invite closes); Skein's workers were detached, and every `FsObjects` call ran in a `spawn_blocking` that outlives its cancelled caller. Now: Skein's `run` waits for workers up to `RunConfig::stop_wait` (new, 30 s by default; the node passes `TestTiming::shutdown`, new, 30 s on the desktop), then aborts them and awaits their end before returning, and releases a stopped worker's lease from its own loop instead of a detached task, never starting a successor while the old worker runs; the node aborts any of its tasks still running after twice that time and awaits them (`tasks::join_within`), tracks every task it spawns outside its list in a `Background` set stopped on shutdown (in `Core` and in the group), and finally calls `FsObjects::close` (new in skein-storage-fs): it waits for storage calls in progress, refuses later ones and releases the owner lock, so a zombie can no longer write and the directory reopens at once. Tests: `closing_frees_the_directory_and_refuses_later_writes` (skein-storage-fs), `a_worker_stuck_past_the_stop_wait_is_dropped_before_run_returns` (skein-engine; hung on the old code), `a_node_stuck_in_a_session_still_frees_its_directory_on_shutdown` (node; `Locked` on the old code at once), `a_shut_down_node_leaves_nothing_holding_its_directory` (group tasks; it did not fail on the old code in a current-thread run and stays as a guard), and the `tasks` unit tests. `regress_to_phase1_for_tests` now shuts the node down itself, since a closed node can no longer write its directory.

- **A peer that hangs up after the key confirmation has refused, on writes too.** The pairing channel already read a closed stream as `Refused`; a write into one was `Unreachable`, so a joiner whose certifier rejected the fingerprint saw "unreachable" when the certifier's refusal and close won the race against the joiner's next message (`a_rejected_fingerprint_adds_nobody`, once in ten parallel copies). Writes map the same way now. A real network failure in the middle of a pairing also reads as refused, which asks the person to start again either way. Regression: `a_peer_hanging_up_mid_pairing_reads_as_refused_on_either_side`.

## 2026-11-26: wave 2, part 1 built (leases across nodes, handover, revocation notices)

Taken without the maintainer while building GROUP.md's "Leases, handover and credentials" and B4, with reasons:

- **One arbiter: the group's server.** A group with a counting `server` node arbitrates every account's lease on that server (`baton-lease-server` on its link, the lowest key when several servers count); a group without one keeps each node's own `lease-cas`, so each desktop leads what it added, as in wave 1. `lease-quorum` needs the mesh (B2 for the mesh is not built) and S3 conditional writes need the `storage` resource (not built), so the bucket and quorum rows of GROUP.md's table wait; two-node groups without a server stay question 47. The arbiter is chosen again on every call, so adopting a server moves every node to it without a restart. While the server is unreachable nothing new is decided and holders stop by themselves (Baton's rule); a server's own maintenance therefore pauses every account it arbitrates (question 70).
- **The lease server is authorized from the group log** (`GroupAuthority`): only counting nodes speak, a node may announce only its certificate's class (a desktop cannot claim a server's priority), and it may take or ask to take over only the lease of an account it holds `lead` on; releasing needs nothing (Baton). A revoked node's renewal is a refused acquire, so it loses its lease within the time-to-live.
- **Eligibility is Skein's, generic.** `RunConfig::eligible` filters, per account, the live nodes the owner is chosen among; the node passes "holds `lead` on `acct-{id}` in the group log", so a server without a grant never takes an account although it outranks every desktop.
- **Skein's engine got lease hooks, a takeover request and `can_run`.** `LeaseHooks::acquired` runs once per lease taken, before the log is claimed (a failure gives the lease back); `LeaseHooks::releasing` before a release, at a clean point (the worker stopped). A run that finds a weaker live holder asks it to hand over. `Engine::set_can_run` makes a node take nothing and release what it holds (the phone before suspension, a server sending accounts back), `Engine::holds_lease` answers whether it may act on a lease now. All generic: Skein names no node, group or credential format.
- **What moves with the lease is the holder's state of the account, sealed to the leaders** (S3 and S4 as built). Skein's per-account control records and trees (now public as `ACCOUNT_CONTROL_TREES` and `ACCOUNT_CONTROL_RECORDS`), the node's account record, the `cmdkey` records and the queued commands, with credentials opened and carried as plaintext inside a seal under the account resource's **secret key** (only `lead` holders have it), bound to the holder's head digest, the epoch and the account. Credentials at rest stay under each node's own keyring: GROUP.md's `GroupKeyring` (Skein's keyring over resource keys) is not built, since sealing the handover is enough for "only lead nodes can open them" and keeps every node's at-rest format as in phase 1. A node with `lead` stores an offer sealed and opens it only when it takes the lease (S3's "only the leaseholder decrypts"); readers never get one.
- **Offers are checked like heads (S4).** The sender must count and hold `lead`, the head must verify and be the sender's own, the offer must not be below the one held (fence, then `seq`) nor below the local head's fence, and the receiver's replica must have reached the head before the offer is stored (so a stored offer never claims events the node lacks). The holder offers on every head change and every round; a node that released keeps offering until somebody else writes (its head is then no longer its own), so a new holder finds the newest state even when the old one released without being asked. An offer without credentials is never made, and a node takes a lease only with an offer newer than its own state, or its own record and credentials.
- **A deposed writer drops its tail.** A head under a higher fence that does not continue the local journal means this node wrote after the next holder continued from an earlier head (it was cut off and still believed it led); that is not a fork. The replica of the account (journal, control records, view rows, staged offer) is dropped and followed again from the start; the dropped events are the provider's changes the new holder sees again from its own cursor. A head under a lower fence is stale everywhere, so a deposed holder's writes never land on another node. `Log::purge_account` (new, in Skein's `Log`) deletes one account's journal and forgets the head the log saw, atomically for concurrent readers, which `purge_account` over objects alone could not (the log refused the purged head as a rollback until restart).
- **Commands follow the lease.** A command waiting in the outbox for an account the node now leads is handled locally, so a node that takes an account over runs what it had issued to the previous owner.
- **A server node is a node class, adopted, not founded.** `NodeBuilder::class(NodeClass::Server)` builds a node that founds a placeholder group (with a member key, as a fresh device does) and offers `Node::server_invite`; the adopting device certifies it, the node moves to the device's group, the placeholder's member key is deleted and the node is rebuilt, exactly like a device joining. The tenant binding and the CLI are `apps/rowboat`'s (not built).
- **B4 needs a per-protocol trust in Baton** (a generic change): `Trust::allows_on(peer, protocol)` and `Trust::reachable(peer)`, defaulting to `allows`, honoured by `baton-link-memory` and `baton-link-iroh` and checked by the link conformance suite. `Membership::trust` admits a revoked node on `revoked` only. A node every peer refused asks for a notice on its next group exchange; it applies the entries only if they chain from its head and verify, then stops leading and calls the app's `on_revoked` hook once. Wipe commands do not travel yet (wipe is not built).
- **Timing.** The lease time-to-live is three heartbeats (30 s on the desktop) and eight in the test profile; multi-node tests use 1 s heartbeats (leases of 8 s), since under six parallel copies of the suites a node's heartbeat loop stalled for seconds and its leases expired and moved back and forth (safely, under growing tokens, but the tests' steps assume a stable holder), and the group exchange runs every four follower polls in the test profile (every 5 minutes on the desktop) so revocation notices arrive in tests.
- **Skein releases off the heartbeat loop.** `run` used to release an unwanted account inline; with a `releasing` hook that offers the state to peers (up to the replication limit) the loop stopped heartbeating meanwhile, the node was judged gone for its other accounts and leases flapped between nodes under load. Releases now run in tasks of their own, the account counted as leaving (no successor worker) until its release is done, and shutdown waits for them within `stop_wait`. Regression: `a_slow_handover_never_holds_heartbeats_up` (hung on the old code).
- **An offer is stored before the account record.** The receiver wrote the record first, so its engine could take the lease between the two writes, find no offer, and lead without credentials (seen under six parallel copies of the node suites as accounts stuck in `ReauthRequired`). The offer goes first now, a node without an offer newer than its own state leads only with its own record and credentials, and no node offers a state without credentials.
- **A flaky Skein proptest** (`associated_data_is_unambiguous` in `skein-keyring-local`) generated account names `AccountId` refuses; it now skips them.

- **One node per tenant, composed by `rowboat-node`.** Each tenant is a `Node` with `Profile::Server` (the desktop's timing, discovery from the table only) and class `Server`, over `<data_dir>/tenants/<id>/node`, its keys in `<secrets_dir>/tenants/<id>` and its mail database in `<cache_dir>/tenants/<id>/view`. - **Binding is a file checked against the node.** `binding.json` (version, tenant, group, genesis hex, node id) is written once the adopted node has been rebuilt; every start checks that the node is adopted into exactly that group, genesis and node id, and a tenant that does not match does not start. The configuration refuses a secrets directory inside the data directory or the other way round, and a cache inside either, so a copy of the data alone opens nothing.
- **The mail database is a cache on the server** (question 74): cleared for a tenant on every start and rebuilt from the sealed journal; the container puts the cache on tmpfs.
- **S3 replaces files, per tenant.** With `[s3]`, `NodeBuilder::store` puts every object of a tenant under `{prefix}/tenants/{id}/` (sealed by the node exactly as on disk); the local directory keeps the lock. GROUP.md's credentials from the `storage` resource configured from the app wait for that resource; the bucket comes from the configuration, its keys from environment variables.
- **One listener, one signal bus, one push registry per host.** `skein-server`'s router is mounted once; every tenant's node shares one `baton-signal-local` bus (topics are scoped to each group, and every node scopes its engine, follower and liveness to its own group) and records push subscriptions in one registry under `<data_dir>/host/objects`, whose exclusive lock also refuses a second `serve` (question 76).
- **Links on a port range.** `link.ports` (`4400-4499`): each tenant records one port at creation and its link always binds it, so devices reach it at the same address after a restart; pairing endpoints take any other free port of the range (question 77). Hints carry `link.advertise`.
- **The CLI works beside `serve` through files** (question 78): `invite` holds the tenant's directory lock while it runs the placeholder node; `serve` starts new bound tenants on its 5-second round; `tenants remove` and `--rebind` write a stop marker and wait (up to two minutes) for `serve` to release the tenant; `status` reads `<data_dir>/host/status.json`, ids and counts only. The commands are `serve`, `invite`, `tenants` (and `tenants remove`) and `status`, as the task named them, instead of GROUP.md's `tenant list`/`tenant remove`; `license` waits for L5b.

Interactive invites also ask the operator to confirm the fingerprint (`server_invite_confirmed`); `--yes` or a non-terminal stdin leaves it to the app, and the fingerprint is still printed.

While the server is down its groups have no arbiter (question 70).

- **Test roots behind a feature.** The container suite's image is built with `test-roots` (`rowboat-node/testing`), which alone accepts `tls.test_ca`; other builds refuse it at validation, so no release path trusts an extra CA.

Eligibility now has two more rules (`LeadEligible`, refreshed before the engine runs and on every replication tick): a node is eligible itself only while it holds state to continue from (its own record and credentials, or an offer), and it treats every other node as ineligible while it holds the account's only state (it can lead it alone, the head is unattested or its own, no peer took an offer yet). Regression `a_server_adopted_before_the_first_sync_still_takes_the_account` (crates/node/tests/handover.rs), shown hanging on the old code.
- **A second node-layer fix, found by the container test: an adopted server gave no address.** The server's side of an adoption sent an empty hint, so the adopting device learned the server's link address only from a later group exchange, which needs one side to dial the other; behind port mapping the server cannot dial a device, so the device never found the server and nothing moved. The server now binds its link before the adoption and sends that hint (the tenant's recorded port, so it holds after the rebuild). The in-memory endpoints reach peers by key, so the regression is the container test, which failed on the old code.

## 2026-11-26: wave 2 review fixes

Taken without the maintainer after a review of wave 2; open items are questions 79 and 80, and 70 and 74 are sharpened.

- **A change of arbiter is a lapse.** The arbiter is picked from each node's view of the group log, and a new one knew nothing of the leases the old one granted: a desktop that adopted a server while its worker was inside a provider session kept acting under its local `lease-cas` while the server took the account from its own empty table. Now `NodeLeases` notices every change of arbiter and calls Skein's new `Engine::lapse` (the holding epoch ends at once, as after lapsed heartbeats; idle workers are woken by the epoch change and stop at their next check), the node offers an account's state only once no worker that lost its lease is left (`Engine::has_worker`), and `baton-lease-server` got `ServerConfig::grace_ms` (generic: for that long after start only the holder its record names may renew), which the node sets to the lease time-to-live. Regressions: `adopting_a_server_while_the_desktop_is_inside_a_run_never_splits_the_lease` (both nodes led at once on the old code), `a_second_server_becoming_the_arbiter_never_splits_the_lease`, `a_server_that_starts_arbitrating_grants_only_renewals_for_its_grace`, `a_lapse_ends_the_epoch_at_once`. A node that learns of the new arbiter later than the grace still has a window (question 79).
- **An offer counts before anything else is known.** A node holding only an offer of an account (no account record yet, since the offering node no longer led it and so described nothing) was not eligible for it while the offering node deferred to it, and nobody led the account (seen as `tenants_never_share_storage_or_keys` hanging under parallel runs, and as most of the handover suite hanging once arbiter changes lapsed). `refresh_eligibility` now walks staged offers too (`Replication::staged_accounts`), and a node describes an account to its readers while it leads it or wrote its journal last.
- **Remote head fences are bounded by the clock, and a fenced claim gives the lease back.** Heads from peers and offers are refused when their fence lies more than `MAX_FENCE_AHEAD_MS` (5 minutes) ahead of this node's clock in microseconds (lease tokens are at least the granting arbiter's wall clock in microseconds), and `Engine::lease` releases a lease whose claim the journal refuses as fenced instead of keeping it, so a predecessor whose clock ran ahead delays the account by at most that skew instead of stranding it. Regressions: `a_claim_refused_by_a_higher_fence_gives_the_lease_back` (the lease stayed and every retry failed on the old code), `a_head_fenced_far_ahead_of_the_clock_is_refused`. Grants signed by the arbiter remain open (question 79).
- **Rebind and removal delete the bucket prefix.** With `[s3]` a rebind found the old node record without its keys and failed for good, and a removal left every sealed object. `Tenants` now deletes everything under the tenant's `system/` and `tenants/` roots through its store before the local directories and keys. Regression: `rebinding_or_removing_a_tenant_kept_in_a_bucket_deletes_its_objects` (the rebind failed on the old code).
- **No terminal, no invite on stdout.** In a container stdout is a log others may read, and without a console the adopting device confirms alone. `serve` now prints the first-run invite only to a terminal; otherwise it writes it to `<secrets_dir>/first-run-invite.txt` (created new, mode 0600, deleted once the invite is used, ends or `serve` stops) and logs the path. Regression: `without_a_terminal_the_first_run_invite_goes_to_a_private_file`.
- **The mail database is deleted when a tenant stops, and the default cache is warned about.** The view directory is now deleted after a tenant's node shuts down as well as before it starts; with the default `cache_dir` (`<data_dir>/cache`) a crash still leaves it in the data volume until the next start, so `serve` warns at startup (question 80).
- **The hand-back does not keep a device syncing while the server is down,** as built: the device holds the lease until it cannot reach the arbiter for a time-to-live. That is the single arbiter of GROUP.md's table and question 70, not a defect of the hand-back, which still leaves the journal at a clean point with the newest state offered; the docs no longer suggest otherwise.
- **Tests.** The container suite's "stored nothing" check now skips the engine's liveness records (moved to the tenant's group in wave 2), and `it.sh` runs the node suites with `--no-fail-fast` so one failing binary does not hide the server test; the restart test waits for the server's mail database instead of reading it at once. The container test opens a new IMAP session before its second append, since the handover now takes a time-to-live longer (the grace) and GreenMail closed the idle one.


## 2026-11-27: the server's silence (question 70 decided)

The maintainer decided question 70: when the group's server is silent longer than a takeover delay (5 minutes by default, configurable per profile, short in the test profile), devices take over the accounts it led by the usual priority among the live nodes holding `lead` and state; when it returns it first catches up (follows the device's journal), then takes the lease back through the normal cooperative handover. Built as GROUP.md's "When the server is silent"; taken without the maintainer while building it, with reasons:

- **The fallback arbiter is a device running `baton-lease-server`**, the first of a fixed order (counting desktops, then counting phones, by key) that answers on the lease protocol, rather than `lease-cas` over the group: there is no shared store without the server, and the lease server, its authority from the group log, its grace and its endorsements already exist. A device takes the role itself only after waiting two heartbeats per device ranked before it, so two devices that fall back together end up on one arbiter. Devices partitioned from each other as well as from the server may each arbitrate: fences and the deposed-writer rule still leave one journal, and the newer one wins.
- **Silence is each device's own view.** A device in fallback probes the server every heartbeat with a `Hello` (never a heartbeat, so the server's liveness and gap records are not disturbed) and returns once the server answered without a break for a quarter of the takeover delay; a server that goes silent again within four takeover delays of coming back doubles that, up to eight times (hysteresis). The test profile's takeover delay is 16 heartbeats (two lease times-to-live).
- **Floors in Baton** (generic, question 79 in part): `Leases::acquire_above(group, key, profile, floor)`, honoured by `baton-lease-cas` and `baton-lease-server` (a new `AcquireAbove` request) through `baton_lease::record::acquire_above`, with a conformance suite (`testing::floors`). A new grant comes above the floor, a renewal below it is granted again above it, a renewal at or above it keeps its token (the first version re-granted at the floor too, so every renewal after a claim bumped the token and the flapping test saw the lease "move" each second). A floor more than 5 minutes ahead of the arbiter's clock is ignored, so a caller cannot push tokens out of reach. The node passes its own head's fence on every acquire.
- **Grants signed by the arbiter** (question 79 in part): Baton's lease server got a generic `Endorse` hook (`ServerConfig::endorse`, `Request::Endorse`, `LeaseClient::endorse`, `LeaseServer::endorse`; only for the lease its record names with that exact token, at most 512 bytes); the node's endorser signs a `rowboat_sync::Grant` (kind, arbiter, group, account, holder, fence) and the holder fetches it once per new token before acting. Heads carry it in a version 2 attestation whose signature covers the grant's hash; version 1 still reads. A head without a grant is followed only over a head without one, so a server group's journals, once granted, never fall back to self-asserted fences. Heads written under the local arbiter (no server) carry no grant, as before.
- **Admission, yielding and the fallback tail** as GROUP.md states them. The server's gap check reads the heartbeat times its lease server stores (Baton: `CasLiveness::last_heartbeat`, `LeaseServer::last_heartbeat`), so it holds across a server restart, and remembers gaps that ended within four takeover delays; the minimum gap is half the takeover delay, which the server and the devices should therefore share. When the server's own record names the server, every device must have been silent: that is what tells a server cut off from all devices from one that a single device claims is silent. A node that admits a fallback holder's head while it sees the server neither takes nor asks to take that account's lease and gives back what it holds (the first version only stopped asking, and the server's record kept naming it while it heartbeated, so the device could never continue); the yield ends when another node continues the journal under a server grant above the fallback fence, or after three takeover delays.
- **What a returning device does with its fallback tail.** Everyone else yields to it and it treats every other node as ineligible, so it takes the lease from the server with its fence as floor and continues its own journal under a server grant; the server then takes the account back cooperatively. It announces such journals every few ticks until then (the server learns of them even when no head changes). One it has not continued two takeover delays after the server came back (the server kept another holder's journal, which it may when a live device held the account under it) is dropped and followed from the group (`Replication::drop_replica`).
- **Commands across a silent takeover.** Taking over from a server that went silent (not on its notice), a device presumes every queued command that cannot be repeated started, once per account and fallback period (Skein: `presume_started`), and settles as uncertain a command it had delivered to that server without an answer (`Host::previous_owner_silent`, attempts remembered in memory). An uncertain send is shown to the person; a send twice cannot be undone. The remaining window (a third device's command redelivered to the new owner) is question 81. Shown meaningful: without `presume_started` the integration test's device sent the message the server had queued.
- **The leaving notice** is signed by the server's node key (`rowboat-leaving-v1`: group, server, time) and sent on the link protocol `leaving` to every candidate device after the server stopped arbitrating (`Node::announce_leaving`, called by `apps/rowboat` after the hand-back). A device believes it only from the counting server of its group, dated within 5 minutes of its clock, and only if a probe right after it fails, so a replayed genuine notice changes nothing while the server answers. The server writes `rowboat/fallback/left` first; on the next start it believes devices' fallback grants for four takeover delays (their silence toward a stopped server proves nothing). `Node::shutdown` alone sends no notice (a rebuild after an adoption must not send devices into fallback).
- **A lease left behind by a worker that lapsed** (Skein, found by `apps/rowboat`'s bucket restart test once a desktop fell back on the leaving notice and came back): a worker that ended on its own (`NotOwner` after its heartbeats lapsed or its arbiter changed) left its lease in the arbiter's record, and once the node preferred another one, nothing released it while it kept heartbeating, so the preferred server could never take the account. `run` now releases such a lease once the account is no longer wanted. Regression `a_lease_left_by_a_worker_that_lapsed_is_released_once_unwanted` (hung on the old code).
- **A fallback arbiter keeps its records in memory**, fresh each time it starts, rather than in the device's state store: that store still held the lease records of the device's own arbiter from before the group had a server, which named the device and so let it renew at once inside the grace meant to keep it from granting while holders of the server's leases may still act.
- **Two fixes found by the new tests.** `NodeLeases` restarted its lease server lazily after `stop()` when a call was still in flight (a killed server kept answering "store failed", which counted as contact, so its devices never fell back); it now refuses to start anything once stopped. Getting a cached client to the server counted as contact; only answered calls count now.
- **Tests** as GROUP.md's attack list and `crates/node/docs/README.md` name them: nine multi-node tests in `crates/node/tests/fallback.rs` on the in-memory link with real time and hang detectors (deterministic checks only: grant kinds, fences, who leads, the fallback's reason, sender calls), unit tests of the watch, the order, the notice, the gap memory and the admission rule, grant and attestation tests in `rowboat-sync`, Baton's floor and endorsement tests, Skein's `presume_started` test. Decoders of the notice and the grant joined the `node_records` and `sync_wire` fuzz targets; the lease server's new requests are covered by `lease_frame`.

## 2026-11-27: review of the server's silence

Taken without the maintainer after the security review of question 70; question 83 is new.

- **The server's own downtime is no device's silence.** After an outage shorter than the takeover delay every device's heartbeats showed a gap longer than half of it, so a device holding `lead` could force its own fallback, grant itself and make the live server follow its journal (proven by a regression test, failing before the fix). `GapWatch` now records when the server started serving and counts a gap that began before that only once it is a full takeover delay long, when the devices did fall back; gaps that begin while it serves keep the half-delay threshold. A graceful leave still believes everyone.
- **A leaving notice only after a finished hand-back.** The notice tells devices the server released everything, so they skip `presume_started` and repeat what cannot be repeated. `apps/rowboat` sends it only when `hand_back` returned true, and `Node::announce_leaving` itself waits two heartbeats for the node's workers and refuses (returns false) while it still leads an account or a worker of one runs; the devices then fall back by silence and settle a started send as uncertain.
- **A server that announced its leave stays stopped.** `announce_leaving` marks the lease server as left for good: its own engine's calls no longer restart it (they get "unavailable"), so devices that fell back on the notice do not see it answering again while it shuts down.
- **A device that sees a live server never follows a fallback grant**, whatever it holds (no journal of the account yet, or a head a fallback arbiter granted); the server judges every fallback head by its view (gaps, newer fence, holder), whatever its own head. Before, a device that had just joined, or a server just granted the account, followed a head a lying device wrote under its own fallback grant.
- **Devices tell a returning server of their fallback journals at once.** While still in fallback, a device whose probes the server answers again announces what it wrote under the fallback grant every tick, so the server yields before its lease server grants again (one time-to-live after it starts) instead of leading beside the device until the device's return delay ends. The review's claim that the device's journal was then dropped did not hold in the test with production ratios (the server imports the device's newer offer when it takes the lease, and a moving journal is announced anyway); the test (`with_production_timing_a_returning_server_continues_the_fallback_journal`, return delay longer than a time-to-live, no head rounds) now also checks the server never leads while the device still holds the account in fallback, and that the server's journal holds the device's event at the device's fallback head. `TestTiming` gained `rounds` (0: never) and `fallback`.
