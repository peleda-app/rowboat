# Open questions

1. **Handover without the old owner's tail.** When the desktop goes away before the phone has replicated its last journal segments, the phone cannot extend a head it has not seen. Options: wait for the old owner (mail stalls), start a new branch and merge by event keys later, or require S3 or a server for multi-device use without the desktop online. Needs a decision together with Skein's head attestation (Baton phase 3).
2. **OAuth refresh tokens that rotate** (Microsoft, some others). Only the leaseholder refreshes, and the new token is sealed to the group before it is used. What happens when the leaseholder refreshed and died before the token reached anyone: the next owner's token is already invalid and the person must sign in again. Acceptable for the first version?
3. **Push deduplication across handovers.** Proposed: the notification key is the message's journal event key, and a node sends only for events it journaled itself. Check against provider moves (a message moved between mailboxes must not notify twice).
4. **Which S3 for people without their own.** Offer a Peleda-provided bucket in the first version, or only "bring your own"?
5. **Blob cache limits on the hosted server without S3**: size per group and maximum age.
6. **Alias services' API keys**: entered by hand, or OAuth where the service offers it (SimpleLogin does)? Which node calls the alias APIs: the owner of the account the alias forwards to, or any node?
7. **Phone as owner on iOS.** Background time is short and at the system's discretion. Does the phone take the lease only while in the foreground, or also from `BGAppRefreshTask`?
8. **Push gateway abuse.** Who may send through it: nodes with a signed statement of the group, rate limited per group and device token.
9. **Dependencies under the license.** rowboat is public under PolyForm Noncommercial (decided 2026-11-25), so everything it builds on must be open or noncommercial. `rinse` (formerly `peleda-content` and `washer`) is open and `bento` (which absorbed `peleda-insight` on 2026-11-26) is open too (MIT OR Apache-2.0, decided 2026-11-26), so the node layer may depend on both.
10. **Licensor name and full license text.** `LICENSE.md` names the PolyForm Noncommercial License 1.0.0, gives its official URL instead of a copy (the license allows that) and the notice "Copyright 2026 the rowboat authors". The maintainer sets the licensor's name for the Required Notice and may add the full license text (nobody may download it on this machine).
11. **CLA placeholders.** `CLA.md` comes from dojo's template and still needs the licensor's legal name and address, the governing law and how it is signed; until then no outside contribution can be accepted.
12. ~~**How to get a commercial license.**~~ Resolved 2026-11-26: the Small Team, Organization and Commercial licenses issued from peleda.app/license ([LICENSING.md](LICENSING.md)); the README's license section says so.
13. **A work mailbox on one's own node.** Does connecting the mailbox an employer gave someone to a node they run themselves count as noncommercial use? The README states it as open.
14. **GitHub rename.** **Resolved (2026-11-26):** the repository is `peleda-app/rowboat` on GitHub.
15. ~~**Container image names.**~~ Resolved 2026-11-25 with the API removal: one image, `ghcr.io/peleda-app/rowboat`; the `-headless` variant and `rowboat-view` are gone, since there is no portal and `skein-view` has no binary.
16. **`skein-view` parses message content outside rinse.** It reads envelopes, bodies, attachments lists and iMIP parts with `mail-parser` and `skein-itip` (it always did), while the workspace rule SEC-2 says untrusted content is parsed only in rinse. Keep it as the app's mail database parser (its fuzz target covers it), or have it take rinse's document model once the app embeds it? [NODE.md](NODE.md) proposes the second for the node: a `MessageParser` hook in `skein-view` that the node fills through rinse, with `mail-parser` kept only for the `skein` binary and Skein's tests. The node does this, and also builds its engine with `without_message_inspection`, so the engine's own iMIP detection never runs in the node's process; invitation summaries return once rinse facts fill `itip`.
17. **Outgoing webhooks.** They were kept (`skein-webhooks` never depended on the API) and are managed with `skein webhook`. Does Peleda's node need them, or should they go once the app manages the node through Baton commands?
18. **Push behind several nodes.** Hints from the push receivers travel in process, so a notification wakes the account only on the node that received it. Route push to the owner, wait for a shared signal backend in Baton, or accept the interval delay?
19. **Snapshots bound to the chain.** `skein-view` now refuses a snapshot at or before its checkpoint or past the attested head, but a follower behind a compacted journal still trusts the snapshot's content, since snapshots carry no hash link to the segment at their `seq`. Add that link (and have the head attest it) so a rebuild is verified like the segments?
20. **A secret in the Graph notification address.** Gmail pushes spend the rate limit only after their path secret matches; Graph notifications have no secret before the body is read, so a flood of forged Graph requests can delay genuine Graph pushes until polling catches up (never Gmail ones). Register Graph subscriptions with a secret in the notification URL as Gmail does (existing subscriptions would be renewed onto it)?
21. **The metrics listener.** The maintainer allowed only push and health inbound. `/metrics` stays as an opt-in listener restricted to loopback, with OTLP for export elsewhere. Keep it, or drop it and rely on OTLP alone?
22. **Split `skein-storage`.** It mixes the storage contract (traits, types, the suite) with its `Objects`-backed implementations and the `baton-state` adapter. Split it into `skein-storage` (traits, types, suite) and `skein-storage-objects` (`ObjectLog`, `ObjectControl`, `ObjectCommands`, `ObjectBlobs`, `CountingObjects`, `ControlState`), an `implementation` running the suite? Every crate that opens storage would depend on both.
23. **A contract for the OAuth token endpoint.** `skein-oauth-http` declares `implements = "skein-oauth"`, but `skein-oauth` is a library (clients, token manager, redirect parsing). Move `TokenEndpoint`, the types in its signature and its conformance suite into a small contract crate (`skein-oauth-endpoint`) that both depend on, or relabel `skein-oauth-http` a `library` that still runs the suite?
24. **What the Organization License is for.** PolyForm Noncommercial already permits charities, educational institutions, public research, public safety or health and environmental organizations and government institutions, whatever their funding. So governments need no Organization License (they have the base license, which cannot be narrowed for copies already out), and for registered charities it only adds certainty and the right to serve beneficiaries and partners. The plan targets organizations of doubtful noncommercial status (newsrooms run as companies, legal-aid practices, unregistered collectives) and that right. Is this the intended scope, and should the page say plainly that governments and charities need no key? Until the maintainer and the lawyer answer, the pages mark that branch as pending and the plan's reading of PolyForm is not presented as settled.
25. **A users cap for the Organization License.** The plan issues it without a cap (`max_users = None`) and lets the review set one. A large international NGO would then get an unlimited free license. Default to no cap, or to a cap (for example 250) that review can raise?
26. **For-profit newsrooms and legal-aid practices.** Eligible when that work is their main activity and their revenue is under a threshold (proposal: EUR 2 million a year)? Or no revenue criterion, judged case by case?
27. **Education and independent research.** Public research and educational institutions are already noncommercial under PolyForm. Add these fields to the Organization License at all (for private schools and independent researchers), or leave them out?
28. **The node's admin resource in Baton.** The license commands need a per-node resource (`node/<node_id>`, leased by that node, created when the node is certified) carrying the `license-*` command classes, granted to owners and admins. Baton has no such resource kind yet; it would also serve other node settings. Define it in Baton (generic, no mention of licenses), or hang the commands on the group's own resource?
29. **Where an installed certificate lives.** Per node in its `StateStore` (the plan: the app installs it on every node it can reach), or once in the group's replicated state so every node, including ones paired later, shows it?
30. **Sanctions and the audience.** Which regimes the licensor follows (EU, UK, US because of US merchants of record), whether a free license counts as making economic resources available, what the country table says (refuse or review per country), and whether humanitarian exemptions and general licenses let human-rights and refugee-aid organizations in embargoed jurisdictions get an Organization License. Until answered: a name hit or an embargoed country holds for review, never refuses automatically.
31. **Accounts for licenses.** The plan reuses hallway's portal accounts (password, optional TOTP, confirmed address) for Small Team and Organization requests. A passwordless, license-only account by email link would be less friction but is a second sign-in mechanism. Keep portal accounts for v1?
32. **Commercial prices and tiers.** Seats tiers (for example 6–25, 26–100, more by agreement), the hosting tier and its unit (hosted users), annual billing only, prices. Not designed: the plan treats plans as catalog data.
33. **An open home for the format.** `rowboat-license` lives in the noncommercial repository, so third parties may read it but not reuse it commercially, and hallway depends on it. Move it to its own open repository (`peleda-license`, MIT OR Apache-2.0) so anyone can verify keys, or keep it here?
34. **Export control of commercial deliveries.** Public source is generally excluded, but commercial licensing and binaries delivered to customers may need classification (EU dual-use 5D002 and its notes, US EAR 740.13(e) or 740.17). The lawyer's answer is needed before the Commercial License goes live.
35. **Who may buy a Commercial License.** Businesses only, or consumers too (then withdrawal rights apply)?
36. **Retention of licensee data.** Proposal: email, licensee name and the holder public keys of bound licenses while valid plus one year; request nonces two hours; serial, kind, dates and acceptance record three years; refused applications deleted 90 days after the decision. The lawyer sets the periods and the legal basis for keeping screening records.
37. **Free licenses as contracts.** Is a free license with click-wrap acceptance a contract in the chosen jurisdiction, does revocation on stated grounds need one, and is "audit on request" (self-certification, at most once a year) enforceable against free licensees? Depends on the licensor's seat (question 10).
38. **Revocation lists above the command cap.** A list travels to nodes inside one `license-revocations` Baton command, so it is capped at 48 KiB (2 500 live serials, 64 revoked keys, 8 withdrawn roots) under Baton's 64 KiB command limit. Revocations of single certificates are expected to be rare, and expired serials are pruned after 30 days. If the live list ever approaches the cap: signed delta lists (each its own object, numbered), carrying the list as a Baton resource over peer fetch, or raising Baton's command limit for this class?
39. **Where account passwords live on a device.** [NODE.md](NODE.md) seals them with Skein's keyring in the node's sealed objects, with the keyring's master key and the objects key only in the platform keystore, so they move with the journal when credentials are sealed to the group (phase 2). The alternative is one keychain item per password, which needs a credential-source hook in `skein-accounts` and a second move later. Keep the spec's choice? *Default taken 2026-11-26, maintainer may change:* the spec's choice (sealed in the node's objects, keys only in the keystore), as built; see [DECISIONS.md](DECISIONS.md).
40. **Encrypting the view database.** `skein-view`'s SQLite file holds subjects, addresses and bodies in the clear (mode 0600, in the app's data directory). Phase 1 as specified relies on disk encryption; SQLCipher would seal it at the cost of a C dependency with its own crypto. Ship phase 1 in the clear, or SQLCipher from the start? *Default taken 2026-11-26, maintainer may change:* phase 1 ships the database in the clear (mode 0600, relying on disk encryption), as built; no SQLCipher dependency.
41. **Pellet on devices.** Pellet parses raw messages itself, and the app allows untrusted bytes only in rinse's worker, so the node cannot run Pellet in process. Phase 1 takes spam from the provider's Junk folder and rinse's authentication facts. Should rinse host Pellet inside its sandbox (a second worker entry point returning Pellet's verdict), and in which phase? *Default taken 2026-11-26, maintainer may change:* Pellet stays out of phase 1 (Junk placement and rinse's authentication facts only); hosting it in rinse's sandbox waits for the maintainer and rinse.
42. **Discovery sources.** Phase 1 uses only the embedded table of well-known providers and probed host guesses. Add autoconfig from the domain itself (HTTPS to `autoconfig.<domain>` and `/.well-known/autoconfig/`), DNS SRV (RFC 6186, needs a resolver dependency), or the ISP database (tells a third party which domain is being set up)? *Default taken 2026-11-26, maintainer may change:* the desktop asks the domain's own autoconfig file (HTTPS, no query string) and its DNS SRV records by default, after the table and before the guesses; the ISP database is not built, since it would tell a third party which domain is being set up. Every discovered server is probed, and a server outside the domain and the known providers needs the person's confirmation. The rule is `rowboat_discover_table::needs_confirmation`; the app never preselects such a candidate and asks a native danger confirmation in `add_account` before the password.
43. **Probing guessed servers.** Discovery returns guessed `imap.`/`smtp.`/`mail.` hosts unverified until Skein's IMAP and SMTP `probe` functions exist (NODE.md change 9). Write the probes in Skein next (TLS verified, greeting and capabilities, no credentials), or drop guesses that were not probed from the desktop profile meanwhile and offer only the table and manual entry? *Default taken 2026-11-26, maintainer may change:* the probes are written (`skein_mail_imap::probe`, `skein_send_smtp::probe`, the node's `ServerProber`), so guesses, autoconfig and SRV candidates are offered only after both servers answered with verified TLS.
44. **Notification inputs on the node.** The node runs bento's notification policy with trust `unknown`, no codes or topics, a 24-hour freshness window and the rate state in memory, so it never escalates (no VIP, time-sensitive or lock-screen code alerts) until authentication facts and extraction are stored per message, and a restart refills the buckets. Default taken 2026-11-26 (DECISIONS.md "new-mail notifications and folder settings for the app"); maintainer may change.
45. **CPace implementation.** [GROUP.md](GROUP.md) (B1) implements CPace in `baton-identity` on `curve25519-dalek`, checked against the draft's test vectors, rather than taking a small third-party crate or RustCrypto's `spake2`. Keep the own implementation (one more piece for the external audit), or depend on a crate? *Default taken 2026-11-26, maintainer may change:* own implementation, no new dependency. Built 2026-11-26 (`baton_identity::Pake`) **without** the draft's test vectors: they could not be fetched (tests and this work stay offline). Until the vectors from `draft-irtf-cfrg-cpace` (ristretto255, SHA-512) are added as a test, interoperability with other CPace implementations is unproven; the protocol's own properties are tested.
46. **Short codes between devices elsewhere.** A typed code carries no address, so two devices not on the same network need a rendezvous. Proposal: a drop mailbox (Peleda's public drop or the person's server) whose box is derived from the code's invite id, carrying only PAKE messages, admitted by proof of work. Build it, and which drop service by default? *Default taken 2026-11-26:* wave 1 builds QR codes everywhere and short codes only for servers and devices with a known address.
47. **Two nodes, no server, no bucket.** `lease-quorum` needs a majority, which is both nodes in a group of two, so a phone cannot lead while the desktop sleeps. Options: the desktop's cooperative release with a reservation for the phone before sleeping, plus a manual "the desktop is gone" takeover after a crash; or require a bucket or server for handover in two-node groups. Recommendation: the first, in wave 2.
48. **The member key on every device.** Baton keeps member keys on desktops and phones; [GROUP.md](GROUP.md) copies it to every desktop and phone of the member at pairing, so any of them can add or renew devices. The alternative (member key on the founding device only) leaves renewals and pairing to one device and recovery. *Default taken 2026-11-26:* copied to every desktop and phone, never to servers.
49. **One server identity per host or per tenant.** One key per host (as `batond`) lets relays and the groups see that tenants share a server; one key per tenant needs an iroh endpoint per tenant. *Default taken 2026-11-26:* one per host. *Built differently 2026-11-26 (`apps/rowboat`):* one identity per tenant, since every tenant is its own `rowboat-node` with its own link, and two iroh endpoints with one key on one host would take each other's connections; one key per host needs one link shared by every tenant's node (a node layer change). Keep per tenant, or build the shared link?
50. **Rekeying the member after a lost device.** A stolen phone holds a copy of the member key, which cannot add nodes alone (`CertifyNode` must also be signed by a counting node) but can sign certificates. Offer `RekeyMember` through the recovery root in the "Lost or stolen" flow, or only revoke the node? *Default taken 2026-11-26:* only revoke; rekeying stays a manual recovery step.
51. **Fingerprint confirmation by QR.** Required for every pairing, also with a 128-bit QR secret, to stop someone who photographed the code. One extra tap per pairing; keep it mandatory? *Default taken 2026-11-26:* mandatory on the device that signs.
52. **Certificate terms for devices.** Desktops and phones get 400-day certificates renewed by themselves in the last 30 days; servers 90 days renewed by a member device. A device offline for more than 400 days must pair again. *Default taken 2026-11-26.*
53. **Self-lock.** After 14 days without a verified contact with the group the node refuses reads and commands until it confirms. Lock reads too (the app's plan) or only commands and sync? *Default taken 2026-11-26:* reads too, `0` turns it off.
54. **Compaction and slow replicas.** The leaseholder keeps segments for replicas that confirmed within 14 days; a replica silent longer rebuilds from the newest segments once question 19 is answered. *Default taken 2026-11-26.*
55. **No recovery until the root is written down.** The founding device keeps the recovery roots until the person confirms writing them down, then deletes them. Should the app refuse to add a second device or a server before that confirmation? *Default taken 2026-11-26:* no refusal, a reminder.
56. **Rebinding a server tenant.** A tenant is bound to the first group that completes its invite. May the operator release the binding from the console (`rowboat invite --tenant {id} --rebind`) for a person who lost every device and the recovery root? It gives the operator the power to hand a tenant's stored data to a new group, though the data stays sealed to keys the new group does not have. *Default taken 2026-11-26:* allowed, logged as an operator action, data of the old group deleted on rebind.
57. **Joining needs a restart.** A device that joins another group by QR moves its node record to that group and asks the app to rebuild the node (`PairingResult::restart_required`), because the running node's tenant is fixed for its lifetime. Only a node with no accounts and no other nodes may join. Is a rebuild in the app acceptable for the onboarding screen, or should the node switch tenants in place (more moving parts in the engine and the follower)? *Default taken 2026-11-26:* rebuild. *Built 2026-11-27 with the app (wave 3):* the app asks a native danger confirmation, the node deletes its old tenant's data after joining, and the app rebuilds it.
58. **Errors for group calls without new variants.** `NodeError` is matched exhaustively by the app, which wave 1 does not touch, so group failures reuse kinds: a wrong or used code, an expired invite and a refusal are `AuthFailed`; a node that may not invite or use an account is `NotFound`; no network is `ServerUnreachable`; a log that does not verify is `ServerRefused`. Add `Forbidden`, `PairingRefused` and `Revoked` together with the app in wave 2? *Default taken 2026-11-26:* reuse until wave 2. *Built 2026-11-27 (wave 3), closed:* `PairingCodeRejected`, `PairingExpired`, `PairingRefused`, `Forbidden` and `PeerUnreachable`, mapped by the app; `Revoked` not added (a revoked node learns it from `GroupEvent::NodeRevoked`).
59. **Local addresses in pairing hints.** The desktop binds its iroh endpoints on every interface with relays and discovery off, so an invite's hint holds only the addresses the endpoint names specifically (none on `0.0.0.0`) and whatever the app passes to `IrohEndpoints::advertise`. Pairing between two devices therefore needs either the app to list the device's LAN addresses, or a relay (Peleda's or the person's server). Which relay ships as the default, and should the node enumerate local addresses itself? *Default taken 2026-11-26:* neither yet; tests run on loopback. *Built 2026-11-27 (wave 3):* `NodeBuilder::advertise` passes the LAN addresses the app finds to `IrohEndpoints::advertise`; the node does not enumerate interfaces itself; no relay ships by default (relays stay off), so devices pair on one network or through a server. Which relay to ship stays open.
60. **Revocation notices before B4.** A revoked node learns of its revocation only once B4 (revocation notices on `peleda/revoked/1`) lands: until then every other node refuses it, but it keeps working alone and does not run the wipe path. Is that acceptable for the first builds that pair devices? *Default taken 2026-11-26:* yes, B4 follows in this wave. B4 built 2026-11-26 (wave 2, part 1): a node every peer refuses asks for its notice on its next group exchange.
61. **Replica health and status.** A node that follows an account shows its health as `unknown`: the owner's status records (health, last sync, errors) are not replicated. Carry them in the owner's head answer (display only), or replicate the account's control state with the journal (wave 2's S4)? *Default taken 2026-11-26:* `unknown` until wave 2.
62. **Remote sends in `outbox()`.** A send issued on a node that follows the account waits in the replication outbox until the owner queued it, and then in the owner's queue; neither shows in the issuing node's `outbox()`. List the replication outbox there too (with the derived command id), or leave the outbox screen to the owner? *Default taken 2026-11-26:* not listed.
63. **Following past a compaction.** A replica that is behind a compacted journal (the owner removed segments a snapshot covers, after 7 days) cannot follow: the chain does not reach its tip, and a new replica cannot start. Until question 19 (snapshots bound to the chain) and question 54 are answered, should owners stop compacting while the group has other nodes? *Default taken 2026-11-26:* compaction unchanged; such a replica reports the account as unreachable and keeps retrying.
64. **A peer's described account after removal.** When the owner removes an account, the resource stays in the group log and the reader keeps its replica and record. Should the owner tell readers (a `removed` flag in its head answer) so they purge the replica? *Default taken 2026-11-26:* not built; the replica stays until the reader is reset.
65. **Accounts added after a server was adopted.** A server holds only the accounts granted to it by name. When the person adds an account on a desktop, should the desktop grant it to the group's servers at once (the person's whole setup on the server), ask, or leave it to the server settings screen? *Default taken 2026-11-26:* not granted until the app asks (wave 2). *Built 2026-11-27 (wave 3):* the app offers every new account to the group's servers through `grant_to_server` behind one switch, on by default; `adopt_server` takes the person's choice at adoption (all by default). Taking a grant back is not built (Baton has no grant removal for servers yet).
66. **Limits per remote address on the pairing endpoint.** Joiners dial with ephemeral keys, so the endpoint cannot limit per peer; two slots, 10 s per handshake message and a one-second pause after each failure bound an attacker but let one client keep both slots busy, and valid guesses at random short ids (10 bits) still burn a server invite now and then: about two attempts a second, so roughly one attempt in a thousand lands on a given pending invite. Expose the remote address through the link contract and limit per address, lengthen the short code's id, or accept this for a server's first run? *Default taken 2026-11-26:* accepted for wave 1; the operator issues a new invite.
67. **Aborting a stuck worker on shutdown.** A worker inside a provider call that has not returned 30 s after shutdown began (a hung IMAP or SMTP session) is now aborted, so the node can stop and its directory reopen. An aborted send never writes its outcome; Skein settles it as uncertain on the next start, as after a crash. Is 30 s right on phones, where the operating system may give an app less time in the background, and should the app pass its own budget? *Default taken 2026-11-26:* 30 s on every profile until wave 3 sets the app's.
68. **Skein's send scheduling on an injected clock.** The undo window and `send_at` are measured with `Timestamp::now()` inside the engine, so node tests cannot move time across a window and test the window's end only with real waits. Give the engine a clock (as the node and `rowboat-group` have), or keep the end of the window tested in Skein alone? *Default taken 2026-11-26:* tested in Skein alone; the node tests use a one-hour window or none.
69. **A send run by a holder that then vanished.** A holder that sends a message and disappears before its next offer leaves the next holder an offer in which the send is still queued and has no start marker, so it may be sent again. Replicate the claim (the start marker) to at least one node with `lead` before a `once` command runs (as GROUP.md asks for rotated refresh tokens, question 2), or accept the window (it needs a crash or partition right after a send)? *Default taken 2026-11-26:* window accepted for wave 2, part 1; offers are pushed on every head change, which shortens it.
70. **A single arbiter.** *Decided by the maintainer 2026-11-27, closed:* when the server is silent longer than a takeover delay (5 minutes by default, per profile), devices take over the accounts it led by the usual priority under a fallback arbiter among themselves, and the returning server first follows their journals, then takes the accounts back cooperatively; a signed leaving notice on graceful shutdown makes them take over at once, and a flapping server does not bounce leases. Built as GROUP.md's "When the server is silent" (DECISIONS.md, 2026-11-27); what is left open is questions 81 and 82.
71. **Credentials at rest under resource keys.** GROUP.md's `GroupKeyring` would seal every node's stored credentials under the account's secret key; built instead: credentials stay under each node's own keyring and travel sealed under the secret key at handover. Rotating the secret key after a revocation therefore protects offers made afterwards, not copies a revoked node already opened (it could have kept them anyway: `secrets_rotation_required`). Build the `GroupKeyring` too? *Default taken 2026-11-26:* not needed for wave 2.
72. **Losing a deposed tail.** A node cut off while it still wrote drops the events it journaled after the head the next holder continued from, and the next holder recovers them from the provider. A flag change or move the deposed node ran in that window is seen again as the provider's state; a send it ran is in question 69. Keep the tail as evidence (like a fork) before dropping it? *Default taken 2026-11-26:* dropped, logged with both heads' positions.
73. **The only copy of an account's state on a lost node.** A node takes over an account only with the previous holder's offer or state of its own; the holder offers on every head change and every round (every 5 minutes on the desktop). A holder revoked or lost before any other node holding `lead` received an offer leaves the account with nobody able to lead it until the person enters the password again on another device. Offer at once when a node gains `lead` (a server adopted, a device paired), or ask the person? *Default taken 2026-11-26:* offers on head changes and rounds only; the app's re-entry of the password (wave 3) is the way out.
74. **The server's mail databases in the clear.** Each tenant's `skein-view` database holds subjects, addresses and bodies in the clear (question 40) while the server runs. The server keeps it in a cache directory (tmpfs in the container) and rebuilds it from the sealed journal on every start, so a copy of the data and secrets volumes at rest holds no plaintext mail, but a running host's memory file system does, and every restart re-renders every message. Does the server need the database at all (it leads accounts but answers no reads), should the node run without a view on servers, or seal it (SQLCipher)? *Default taken 2026-11-26:* kept, in the cache, rebuilt on start. Deleted on every stop too since the wave 2 review; only a crash with the cache inside the data directory (the default) leaves it at rest (question 80).
75. **Content pipeline on the server.** The server renders messages with `rinse-mail-direct` in process, which rinse documents as fit for the server node but which is no OS wall (SEC-2 asks for rinse's sandboxed workers everywhere). Ship `rinse-worker` in the image and use `rinse-mail-process` with `rinse-sandbox-linux` (needs user namespaces and seccomp in the container, often refused by default container runtimes)? *Default taken 2026-11-26:* direct until the sandbox is checked inside containers.
76. **Push registry shared by a host's tenants.** Every tenant's node records its provider push subscriptions in one host registry (`<data_dir>/host/objects`, `system/push/...`), which the one listener reads. Graph subscriptions are keyed by the provider's random id, but Gmail's are keyed by the address: two tenants holding the same Gmail account would overwrite each other's record, and the hint goes to the last one. Only OAuth accounts push, and the node offers no OAuth yet. Key Gmail records by tenant as well (a Skein change), or refuse a second tenant for one address? *Default taken 2026-11-26:* left as is until OAuth accounts exist.
77. **One UDP port per tenant.** Each tenant's link keeps one port of `link.ports` (100 by default), so a host serves at most as many tenants as the range has ports, minus those pairing endpoints use. Share one port among all tenants (the shared link of question 49), or keep a range sized by the operator? *Default taken 2026-11-26:* a range, `4400-4499` by default.
78. **The CLI and `serve` coordinate through files.** Without a management API, `invite` and `tenants remove` work on a tenant's directory (its lock), `serve` picks new bound tenants up every 5 s and stops a tenant when a stop marker appears, and `status` reads a file `serve` writes every 5 s. A local control socket would answer at once and report live state. Keep files (nothing listens), or add a Unix socket readable by the operator only? *Default taken 2026-11-26:* files.
79. **Leases bound to their arbiter.** Lease tokens are unsigned and a head's fence is self-asserted by its signer, so the node bounds remote fences by its clock (5 minutes ahead at most) and a fenced claim gives the lease back; a node holding `lead` can still make an account wait up to that bound, and a node that learns of a new arbiter later than the new server's grace (one time-to-live) may act beside it until it does. Have the lease server sign each grant (group, key, node, fence) and carry the grant in heads, checked against the current arbiter, and let an acquire pass the local head's fence as a floor for the next token? *Default taken 2026-11-26 (wave 2 review):* not yet. *Built in part 2026-11-27 (question 70):* every arbiter signs its grants, heads carry them (attestation version 2), and every acquire passes the local head's fence as a floor; a grant is checked against the arbiter's standing and class in the group log (a counting server, or a counting device for a fallback grant), not against which server is the current arbiter, and a head without a grant is still accepted over one without. Still open: refuse grants of a server that is no longer the lowest counting one, and the window of a node that learns of a new arbiter after its grace.
80. **The server's cache directory by default.** `cache_dir` defaults to `<data_dir>/cache`, so after a crash the data volume holds plaintext mail until the next start (`serve` warns; the example configuration and the container use a tmpfs). Make `cache_dir` required, refuse a cache inside the data directory, or default to a runtime directory such as `/run/rowboat`? *Default taken 2026-11-26 (wave 2 review):* the default stays, with the warning and deletion on stop.
81. **A command redelivered across a silent takeover.** A command a third device sent to the server, which the server ran (a send) just before it was cut off, whose answer was lost, is redelivered from that device's outbox to the device that took over; that owner runs it unless the command's `cmdkey` record reached it in an offer, so a send may go out twice. The issuer itself settles such a command uncertain when it is the one that took over, and a device that takes over presumes its imported queue started, but a new owner cannot tell a command the silent server ran from one that never reached it. Have a new owner that took over from a silent server answer every unrepeatable command created before its takeover with `Uncertain` (a send issued while the server was down would then be reported uncertain though it never left), or accept the window? *Default taken 2026-11-27:* the window is accepted and written down (GROUP.md, "When the server is silent").
82. **A lone device and its server.** In a group of one device and a server, "every device was silent to the server" is that device's own gap: a device that stops talking to the server for half the takeover delay and then presents its own fallback grant replaces the server's journal (the server yields; the provider is the truth, so nothing is lost but the server's journal tail). With a second device talking to the server it cannot. It is the person's own device, holding `lead`; should a server alone with one device refuse fallback grants while it holds the account itself, at the cost of a real cut-off between them keeping the server's journal? Relatedly, `apps/rowboat` has no setting for the takeover delay (the server uses the default 5 minutes to judge devices' gaps), so devices configured with a shorter delay are believed only after half the server's. *Default taken 2026-11-27:* accepted; the delay stays a node builder setting.
83. **A returning server that grants before it hears of the fallback journals.** Devices announce their fallback heads to the server every tick once its probes answer again, and offers reach it too, but nothing makes the server wait for them: if none arrives within its grace (one time-to-live, 30 s; a device probes every heartbeat, 10 s), the server leads its own journal beside the fallback holder until it hears of the holder's head, and a send the holder ran in that window may also run on the server from the queue it imported. Keep the server from leading accounts it led before a crash until every candidate device answered a head request or the takeover delay passed? *Default taken 2026-11-27:* the push only; the window is written down.
