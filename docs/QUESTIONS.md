# Open questions

1. **Handover without the old owner's tail.** When the desktop goes away before the phone has replicated its last journal segments, the phone cannot extend a head it has not seen. Options: wait for the old owner (mail stalls), start a new branch and merge by event keys later, or require S3 or a server for multi-device use without the desktop online. Needs a decision together with Skein's head attestation (Baton phase 3).
2. **OAuth refresh tokens that rotate** (Microsoft, some others). Only the leaseholder refreshes, and the new token is sealed to the group before it is used. What happens when the leaseholder refreshed and died before the token reached anyone: the next owner's token is already invalid and the person must sign in again. Acceptable for the first version?
3. **Push deduplication across handovers.** Proposed: the notification key is the message's journal event key, and a node sends only for events it journaled itself. Check against provider moves (a message moved between mailboxes must not notify twice).
4. **Which S3 for people without their own.** Offer a Peleda-provided bucket in the first version, or only "bring your own"?
5. **Blob cache limits on the hosted server without S3**: size per group and maximum age.
6. **Alias services' API keys**: entered by hand, or OAuth where the service offers it (SimpleLogin does)? Which node calls the alias APIs: the owner of the account the alias forwards to, or any node?
7. **Phone as owner on iOS.** Background time is short and at the system's discretion. Does the phone take the lease only while in the foreground, or also from `BGAppRefreshTask`?
8. **Push gateway abuse.** Who may send through it: nodes with a signed statement of the group, rate limited per group and device token.
9. **Dependencies under the license.** rowboat is public under PolyForm Noncommercial (decided 2026-11-25), so everything it builds on must be open or noncommercial. `rinse` (formerly `peleda-content` and `washer`) is open and `bento` (which absorbed `peleda-insight` on 2026-11-26) is open too (MIT OR Apache-2.0, decided 2026-11-26), so the node layer may depend on both.
10. **Licensor name and full license text.** `LICENSE.md` names the PolyForm Noncommercial License 1.0.0, gives its official URL instead of a copy (the license allows that) and the notice "Copyright 2026 the rowboat authors". The maintainer sets the licensor's name for the Required Notice and may add the full license text (nobody may download it on this machine).
11. **CLA placeholders.** `CLA.md` comes from dojo's template and still needs the licensor's legal name and address, the governing law and how it is signed; until then no outside contribution can be accepted.
12. ~~**How to get a commercial license.**~~ Resolved 2026-11-26: the Small Team, Organization and Commercial licenses issued from peleda.app/license ([LICENSING.md](LICENSING.md)); the README's license section says so.
13. **A work mailbox on one's own node.** Does connecting the mailbox an employer gave someone to a node they run themselves count as noncommercial use? The README states it as open.
14. **GitHub rename.** **Resolved (2026-11-26):** the repository is `peleda-app/rowboat` on GitHub.
15. ~~**Container image names.**~~ Resolved 2026-11-25 with the API removal: one image, `ghcr.io/peleda-app/rowboat`; the `-headless` variant and `rowboat-view` are gone, since there is no portal and `skein-view` has no binary.
16. **`skein-view` parses message content outside rinse.** It reads envelopes, bodies, attachments lists and iMIP parts with `mail-parser` and `skein-itip` (it always did), while the workspace rule SEC-2 says untrusted content is parsed only in rinse. Keep it as the app's mail database parser (its fuzz target covers it), or have it take rinse's document model once the app embeds it? [NODE.md](NODE.md) proposes the second for the node: a `MessageParser` hook in `skein-view` that the node fills through rinse, with `mail-parser` kept only for the `skein` binary and Skein's tests. The node does this, and also builds its engine with `without_message_inspection`, so the engine's own iMIP detection never runs in the node's process; invitation summaries return once rinse facts fill `itip`.
17. **Outgoing webhooks.** They were kept (`skein-webhooks` never depended on the API) and are managed with `skein webhook`. Does Peleda's node need them, or should they go once the app manages the node through Baton commands?
18. **Push behind several nodes.** Hints from the push receivers travel in process, so a notification wakes the account only on the node that received it. Route push to the owner, wait for a shared signal backend in Baton, or accept the interval delay?
19. **Snapshots bound to the chain.** `skein-view` now refuses a snapshot at or before its checkpoint or past the attested head, but a follower behind a compacted journal still trusts the snapshot's content, since snapshots carry no hash link to the segment at their `seq`. Add that link (and have the head attest it) so a rebuild is verified like the segments?
20. **A secret in the Graph notification address.** Gmail pushes spend the rate limit only after their path secret matches; Graph notifications have no secret before the body is read, so a flood of forged Graph requests can delay genuine Graph pushes until polling catches up (never Gmail ones). Register Graph subscriptions with a secret in the notification URL as Gmail does (existing subscriptions would be renewed onto it)?
21. **The metrics listener.** The maintainer allowed only push and health inbound. `/metrics` stays as an opt-in listener restricted to loopback, with OTLP for export elsewhere. Keep it, or drop it and rely on OTLP alone?
22. **Split `skein-storage`.** It mixes the storage contract (traits, types, the suite) with its `Objects`-backed implementations and the `baton-state` adapter. Split it into `skein-storage` (traits, types, suite) and `skein-storage-objects` (`ObjectLog`, `ObjectControl`, `ObjectCommands`, `ObjectBlobs`, `CountingObjects`, `ControlState`), an `implementation` running the suite? Every crate that opens storage would depend on both.
23. **A contract for the OAuth token endpoint.** `skein-oauth-http` declares `implements = "skein-oauth"`, but `skein-oauth` is a library (clients, token manager, redirect parsing). Move `TokenEndpoint`, the types in its signature and its conformance suite into a small contract crate (`skein-oauth-endpoint`) that both depend on, or relabel `skein-oauth-http` a `library` that still runs the suite?
24. **What the Organization License is for.** PolyForm Noncommercial already permits charities, educational institutions, public research, public safety or health and environmental organizations and government institutions, whatever their funding. So governments need no Organization License (they have the base license, which cannot be narrowed for copies already out), and for registered charities it only adds certainty and the right to serve beneficiaries and partners. The plan targets organizations of doubtful noncommercial status (newsrooms run as companies, legal-aid practices, unregistered collectives) and that right. Is this the intended scope, and should the page say plainly that governments and charities need no key? Until the maintainer and the lawyer answer, the pages mark that branch as pending and the plan's reading of PolyForm is not presented as settled.
25. **A users cap for the Organization License.** The plan issues it without a cap (`max_users = None`) and lets the review set one. A large international NGO would then get an unlimited free license. Default to no cap, or to a cap (for example 250) that review can raise?
26. **For-profit newsrooms and legal-aid practices.** Eligible when that work is their main activity and their revenue is under a threshold (proposal: EUR 2 million a year)? Or no revenue criterion, judged case by case?
27. **Education and independent research.** Public research and educational institutions are already noncommercial under PolyForm. Add these fields to the Organization License at all (for private schools and independent researchers), or leave them out?
28. **The node's admin resource in Baton.** The license commands need a per-node resource (`node/<node_id>`, leased by that node, created when the node is certified) carrying the `license-*` command classes, granted to owners and admins. Baton has no such resource kind yet; it would also serve other node settings. Define it in Baton (generic, no mention of licenses), or hang the commands on the group's own resource?
29. **Where an installed certificate lives.** Per node in its `StateStore` (the plan: the app installs it on every node it can reach), or once in the group's replicated state so every node, including ones paired later, shows it?
30. **Sanctions and the audience.** Which regimes the licensor follows (EU, UK, US because of US merchants of record), whether a free license counts as making economic resources available, what the country table says (refuse or review per country), and whether humanitarian exemptions and general licenses let human-rights and refugee-aid organizations in embargoed jurisdictions get an Organization License. Until answered: a name hit or an embargoed country holds for review, never refuses automatically.
31. **Accounts for licenses.** The plan reuses hallway's portal accounts (password, optional TOTP, confirmed address) for Small Team and Organization requests. A passwordless, license-only account by email link would be less friction but is a second sign-in mechanism. Keep portal accounts for v1?
32. **Commercial prices and tiers.** Seats tiers (for example 6–25, 26–100, more by agreement), the hosting tier and its unit (hosted users), annual billing only, prices. Not designed: the plan treats plans as catalog data.
33. **An open home for the format.** `rowboat-license` lives in the noncommercial repository, so third parties may read it but not reuse it commercially, and hallway depends on it. Move it to its own open repository (`peleda-license`, MIT OR Apache-2.0) so anyone can verify keys, or keep it here?
34. **Export control of commercial deliveries.** Public source is generally excluded, but commercial licensing and binaries delivered to customers may need classification (EU dual-use 5D002 and its notes, US EAR 740.13(e) or 740.17). The lawyer's answer is needed before the Commercial License goes live.
35. **Who may buy a Commercial License.** Businesses only, or consumers too (then withdrawal rights apply)?
36. **Retention of licensee data.** Proposal: email, licensee name and the holder public keys of bound licenses while valid plus one year; request nonces two hours; serial, kind, dates and acceptance record three years; refused applications deleted 90 days after the decision. The lawyer sets the periods and the legal basis for keeping screening records.
37. **Free licenses as contracts.** Is a free license with click-wrap acceptance a contract in the chosen jurisdiction, does revocation on stated grounds need one, and is "audit on request" (self-certification, at most once a year) enforceable against free licensees? Depends on the licensor's seat (question 10).
38. **Revocation lists above the command cap.** A list travels to nodes inside one `license-revocations` Baton command, so it is capped at 48 KiB (2 500 live serials, 64 revoked keys, 8 withdrawn roots) under Baton's 64 KiB command limit. Revocations of single certificates are expected to be rare, and expired serials are pruned after 30 days. If the live list ever approaches the cap: signed delta lists (each its own object, numbered), carrying the list as a Baton resource over peer fetch, or raising Baton's command limit for this class?
39. **Where account passwords live on a device.** [NODE.md](NODE.md) seals them with Skein's keyring in the node's sealed objects, with the keyring's master key and the objects key only in the platform keystore, so they move with the journal when credentials are sealed to the group (phase 2). The alternative is one keychain item per password, which needs a credential-source hook in `skein-accounts` and a second move later. Keep the spec's choice? *Default taken 2026-11-26, maintainer may change:* the spec's choice (sealed in the node's objects, keys only in the keystore), as built; see [DECISIONS.md](DECISIONS.md).
40. **Encrypting the view database.** `skein-view`'s SQLite file holds subjects, addresses and bodies in the clear (mode 0600, in the app's data directory). Phase 1 as specified relies on disk encryption; SQLCipher would seal it at the cost of a C dependency with its own crypto. Ship phase 1 in the clear, or SQLCipher from the start? *Default taken 2026-11-26, maintainer may change:* phase 1 ships the database in the clear (mode 0600, relying on disk encryption), as built; no SQLCipher dependency.
41. **Pellet on devices.** Pellet parses raw messages itself, and the app allows untrusted bytes only in rinse's worker, so the node cannot run Pellet in process. Phase 1 takes spam from the provider's Junk folder and rinse's authentication facts. Should rinse host Pellet inside its sandbox (a second worker entry point returning Pellet's verdict), and in which phase? *Default taken 2026-11-26, maintainer may change:* Pellet stays out of phase 1 (Junk placement and rinse's authentication facts only); hosting it in rinse's sandbox waits for the maintainer and rinse.
42. **Discovery sources.** Phase 1 uses only the embedded table of well-known providers and probed host guesses. Add autoconfig from the domain itself (HTTPS to `autoconfig.<domain>` and `/.well-known/autoconfig/`), DNS SRV (RFC 6186, needs a resolver dependency), or the ISP database (tells a third party which domain is being set up)? *Default taken 2026-11-26, maintainer may change:* the desktop asks the domain's own autoconfig file (HTTPS, no query string) and its DNS SRV records by default, after the table and before the guesses; the ISP database is not built, since it would tell a third party which domain is being set up. Every discovered server is probed, and a server outside the domain and the known providers needs the person's confirmation. The rule is `rowboat_discover_table::needs_confirmation`; the app never preselects such a candidate and asks a native danger confirmation in `add_account` before the password.
43. **Probing guessed servers.** Discovery returns guessed `imap.`/`smtp.`/`mail.` hosts unverified until Skein's IMAP and SMTP `probe` functions exist (NODE.md change 9). Write the probes in Skein next (TLS verified, greeting and capabilities, no credentials), or drop guesses that were not probed from the desktop profile meanwhile and offer only the table and manual entry? *Default taken 2026-11-26, maintainer may change:* the probes are written (`skein_mail_imap::probe`, `skein_send_smtp::probe`, the node's `ServerProber`), so guesses, autoconfig and SRV candidates are offered only after both servers answered with verified TLS.
44. **Notification inputs on the node.** The node runs bento's notification policy with trust `unknown`, no codes or topics, a 24-hour freshness window and the rate state in memory, so it never escalates (no VIP, time-sensitive or lock-screen code alerts) until authentication facts and extraction are stored per message, and a restart refills the buckets. Default taken 2026-11-26 (DECISIONS.md "new-mail notifications and folder settings for the app"); maintainer may change.
