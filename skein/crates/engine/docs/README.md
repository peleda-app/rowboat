# skein-engine

Turns provider changes into the journal and runs queued commands, under a fenced lease on each account.

Leases, liveness and signals come from the contracts of Baton, the coordination library Skein uses (`baton-lease`, `baton-signal`). The engine receives them as `Arc<dyn baton_lease::Leases>`, `Arc<dyn baton_lease::Liveness>` and `Arc<dyn baton_signal::Signal>` and never checks which implementation it got.

## Usage

```rust
let state: Arc<dyn baton_state::StateStore> = Arc::new(ControlState::new(storage.control.clone()));
let liveness: Arc<dyn Liveness> = Arc::new(OneGroupLiveness::nodes(Arc::new(CasLiveness::new(state.clone(), 30_000))));
let leases = Arc::new(CasLeases::new(state, liveness.clone()));
let engine = Engine::new(storage, leases, signal, node_profile(node_id, 1, true));
engine.sync_account(&AccountConfig::new(tenant, account), &provider).await?;
engine.run_commands(&config, &provider).await?;
skein_engine::run(engine, directory, RunConfig::new(liveness), shutdown).await;
```

## Leases

- **Mapping.** A tenant is the Baton group of the same id and an account the lease key of the same id (`skein_core::coordination`); the lease on `(group(tenant), lease_key(account))` makes a node the account's owner, and its fencing token is what storage checks.
- **Profiles.** `node_profile(node, weight, always_on)`: an always-on node is `NodeClass::Server`, any other `NodeClass::Desktop`, both able to run with `weight` as capacity (zero never holds a lease). Leases go to the strongest class alive first, then by weighted rendezvous hashing over `(tenant, account, node)`, the same hash as before for nodes of one class.
- **Every run** (`run_commands`, `sync_account`, `run_pim_commands`, `sync_collections`) takes or renews the lease and claims the log with its token. A pending takeover by a stronger node is honoured there, at the start of a run: the lease is released and the run fails with `NotOwner`.
- **Holder self-expiry.** Under `run`, the engine stops acting on its leases once its last successful heartbeat started more than the liveness time-to-live less a fifth ago: runs fail with `NotOwner` before they take the lease, and before a command's started marker is stored (so before anything reaches a provider or a sending service). A lapse is final for the leases taken before it: once a heartbeat succeeds only after the window had closed, a run still working with a lease taken or renewed before the lapse fails with `NotOwner` at its next started marker or iTIP mailing even though the node holds again, since another node may have taken the account meanwhile; the next run takes the lease again. Writes to storage are fenced anyway; this keeps the side effects storage cannot fence single. Called without `run`, there is no such bound and the caller keeps the node's heartbeats.
- **Mailbox lists.** When the directory returns an account whose `include` or `exclude` differs from what its running worker was started with, `run` stops that worker and starts a new one with the new lists once the old one has ended, so a skipped mailbox stops syncing and an unskipped one starts without a restart.
- **Liveness.** `run` heartbeats once per `RunConfig::heartbeat` in `RunConfig::nodes` (`NODES_GROUP`, `_nodes`, by default) and reads live nodes from there. The liveness given to `run` must be the one the leases judge holders by and must answer for every tenant's group what it answers for that group: `OneGroupLiveness` does this, so a node heartbeats once per interval whatever the number of tenants.
- **Eligibility.** `RunConfig::eligible` (an `Eligible`) narrows, per account, the live nodes the owner is chosen among (for example those the deployment granted the right to lead it); every live node by default.
- **Takeover requests.** A run that finds the lease held by another live node asks it to hand over (`request_takeover`; refused unless this node is stronger) and fails with `NotOwner`.
- **Lease hooks.** `Engine::with_lease_hooks` (`LeaseHooks`): `acquired` runs once for every lease the node takes and has not acted on since its heartbeats last lapsed, after the grant and before the log is claimed with its token (a failure gives the lease back and the run ends with it); `releasing` runs before the node gives up a lease it holds, at a clean point. A node uses them to move what lives beside the journal with the lease. A journal already claimed with a higher token makes `lease` give the lease back and fail with `NotOwner`, so an account never stays with a node that cannot write it.
- **Lapse on demand.** `Engine::lapse` ends the holding epoch at once, as lapsed heartbeats do (for a node whose arbiter changed: the new one knows nothing of the old one's leases); workers waiting for mail or their interval are woken by every epoch change. `Engine::has_worker` says whether `run` keeps a worker for an account or is still releasing it.
- **Running or not.** `Engine::set_can_run(false)` announces from the next heartbeat that the node cannot run work: it takes nothing, and under `run` its workers stop and their leases are released. `Engine::holds_lease(tenant, account)` says whether the node may act on an account's lease now.
- **Presumed starts.** `presume_started(storage, tenant, account)` marks every queued command of the account that cannot be repeated safely (move, delete, append, send; not flag or label changes, refetches or collection commands) as started unless it already has a marker, so the next run reports it uncertain instead of carrying it out; idempotent, a cancellation is kept. For a node taking an account over from a holder that may still have been running the same queue (rowboat: a server that went silent).
- **Errors.** `EngineError::NotOwner` when another node holds the lease, a takeover is pending or the lease may have expired; `EngineError::Lease(LeaseError)` when leases cannot be decided (the run did nothing).
- **Release.** An account the node no longer prefers is released once its worker has stopped (checked on each heartbeat; no new worker starts for it until then), also when the worker ended on its own (after a lapse) and the lease stayed in the arbiter's record (regression `a_lease_left_by_a_worker_that_lapsed_is_released_once_unwanted`); on shutdown, every lease the node still holds is released, so another node can take the accounts at once instead of after the time-to-live. A worker still busy `RunConfig::stop_wait` (30 s by default) after shutdown began is aborted, and `run` returns only once every worker has been dropped.

## Guarantees

- **Writes that never ran:** the session is opened before a command's started marker is stored, and when `apply` answers `Auth`, `Config` or `Throttled` (nothing changed) the marker is removed, so the command runs again on a later try instead of turning `write_uncertain`; `set_flags`, `set_labels` and `refetch` are safe to repeat.
- **Order of writes** per batch: blobs, previews (signals), events (fenced), cursor (compare-and-swap with the token). A crash anywhere loses nothing; a crash between events and cursor makes the next run drop the repeated events by their keys, so every change is journaled once. Account-level events (`mailbox_upserted`, `mailbox_deleted`, `first_sync_completed`, `account_capabilities`, journaled when the provider's `capabilities` change) are checked the same way against what was journaled between the last saved account state and the start of the run, which is empty without a crash and costs no read.
- **Fencing:** a run first claims the account's token in the log; a node that lost the account fails with `NotOwner` on its next write.
- **Commands** run once in submission order. Before a move, delete or append reaches the provider a marker is stored; after a crash such a command is reported `write_uncertain` rather than run twice. Results carry the command id as `origin` and its `trace`.
- **Sending** (`send` commands, senders from `Engine::with_senders(Arc<dyn SenderDirectory>)`):
  - a send is due at its `send_at`, but never before the end of the undo window, `created_at + SendPolicy::undo_ms` (`0` by default, which turns the window off; a later `send_at` is kept, an earlier one is moved to the end of the window; `respond_invitation` waits for the window too, dry runs do not). Until then it stays queued and is skipped without holding up later commands; `CommandReport::waiting` and `next_due` say so (it runs on the first run after it is due, so within the worker's interval), and `DELETE .../commands/{id}` still stops it;
  - a scheduled send is per message: there is no per-recipient send time, so consumers submit one `send` per send time;
  - a dry run (`dry_run: true`) makes every check below and resolves the sender, then records `write_applied` and a `send_result` with `dry_run: true` and no refusals; it never hands anything to the sender and never saves to Sent, and it fails with the same reasons as a real send;
  - the envelope is checked (`invalid_envelope`), the blob loaded (`blob_missing`) and the bytes validated (`invalid_message`); an account without a sender fails with `no_sender`;
  - the started marker is stored before the message is handed over, so a crash after sending is reported `write_uncertain` and never sent again; `SendError::Uncertain` is also `write_uncertain`;
  - an error that guarantees nothing was sent and may pass (`Unavailable`, `Temporary`, `Throttled`, temporary refusals) keeps the command queued with a try counter at control path `sending/{account}/{command}` and a backoff (`SendPolicy`: 8 tries, 1 minute doubling to at most 1 hour by default, `Engine::with_send_policy`), then fails with `gave_up`. When the service asked for a wait (`SendError::retry_after()`), the next try is at the later of the backoff and that wait, the wait capped at one hour; other errors fail with `SendError::reason()` (`auth`, `refused`, `recipients_refused`, `too_large`, `invalid`);
  - on success `write_applied` is followed by `send_result`, with the sender's `message_id` (the `Message-ID` recipients got, when the service replaced it) and `provider_message_id` when it reported them; when the sender does not keep a copy and `save_to_sent` names a mailbox, the message is appended there with `\Seen` (a failed copy does not fail the send: `sent_copy: failed`). The mail session is only opened when a command needs it.
  - when the engine appends that copy and the sender reported a delivered `Message-ID` that differs from the message's own (Amazon SES), the copy carries the delivered one, so recipients' replies thread with it: the first `Message-ID` field's value is replaced (the name keeps its spelling, a folded value becomes one line), the original value follows in a new `X-Skein-Original-Message-ID` field (`skein_engine::ORIGINAL_MESSAGE_ID`), a message without a `Message-ID` gets one at the end of its header block, new lines end like the message's own, and every other byte, the body included, is unchanged. A delivered value that is not `<left@right>` of printable ASCII is ignored. The command's blob in the journal stays the client's bytes; the copy that comes back through sync (`message_added` in Sent) is the rewritten one. Senders whose service keeps the copy (Gmail, Graph, JMAP) are never rewritten.
  - The handed-over envelope carries the command id as DSN `ENVID`.
- **Health:** `account_health_changed` only on changes (`healthy`, `reauth_required`, `throttled`, `degraded`).
- **Status record:** besides the journal, every mail sync run, calendar and contacts run and send that reached the sending service records its outcome in one small record per account, control path `status/{account}` (`skein_core::AccountStatus`), read with `load_status(control, tenant, account)` in one control-store read. A change of outcome or of `resync_required` is written at once; an unchanged one at most once every `STATUS_REFRESH_MS` (60 s), so a quiet healthy account costs one read and no write per run, and `last_ok_at`/`last_error_at` may lag by up to a minute. Writes are compare-and-swap with a few retries, carry the owner's fencing token (an older owner writes nothing) and never fail the run: a storage error only skips the update. `NotOwner` is not recorded. `resync_required` turns true when a run that saw a cursor reset (`resync_required` event) failed before finishing, stays true across further failures and clears on the next successful run of that domain. Send records only account-level failures (`auth`, `throttled`, `invalid` as `config`, and `unavailable`, `temporary`, `uncertain` as `network`), never per-message refusals; the engine validates the envelope and message before handing them over, so an `invalid` from the sender or the sender directory means the account's sending settings or the service account cannot send (such as an unusable endpoint, or an SES account that is suspended or paused); dry runs are not recorded. Mail errors map `Auth`→`auth_failed`, `Config`→`config`, `Throttled`→`throttled`, `Network`→`network`, `Protocol` and `MailboxNotFound`→`protocol`, storage→`storage`; calendar and contacts errors alike.
- **Gmail labels:** when an `All` mailbox is synced, label mailboxes are skipped; their messages come from `All` with labels.
- **`run`:** heartbeats, picks accounts with `baton_lease::preferred` over live nodes, keeps one worker per owned account that syncs on push, on command hints (`commands/{account}`), and on the interval, with exponential backoff and `retry_after`; releases accounts it no longer prefers. `Engine::let_go(tenant, account)` resolves once `run` has finished a pass over the directory that began after the call and has no worker for the account left (a stopped worker's lease released), or once `run` has returned; a caller that paused or removed the account first then knows nothing syncs it any more.
- Previews go to `preview/{account}`, head hints to `heads/{account}` as signals in the tenant's group.
- Logs carry account ids, counts and timings only.

## Snapshots and retention

- `snapshot_account(tenant, account, min_new)` folds the events since the latest snapshot into a new one once at least `min_new` were appended; any node may do it, since a snapshot is derived from the committed log.
- `compact_account(tenant, account, retain)` removes the events the latest snapshot covers once that snapshot is older than `retain`, so a consumer that falls behind by less than `retain` never needs the snapshot.
- `run` calls `maintain` after every successful sync with `RunConfig::maintenance` (defaults: a snapshot every 5,000 events, 7 days of retention).
- `AccountObserver` — `after_run(tenant, account)`, called by an account's worker after every successful run (commands, sync, maintenance), in the order of `RunConfig::observers` (empty by default), while the node owns the account; calls for one account never overlap. An `ObserverError` (ids and kinds only) is logged and never fails the worker. `skein-webhooks` delivers webhooks this way.
- Replay protection reads from the first remaining event when the log was compacted.
- Blobs are not expired by the engine: use the object store's lifecycle rules on `tenants/*/blobs/` (for example 30 days) and the `refetch` command for blobs a consumer needs after they expired.

## Push

With `RunConfig::push` (a `skein_push::Renewer`, the node's public URL and an optional Gmail topic), the worker keeps the account's push subscription alive after each successful run, renewing when a third of its lifetime is left, and wakes on hints published on `push/{account}` by the server's push routes, besides `commands/{account}`.

## Calendars and contacts

`sync_collections(config, pim_provider)` and `run_pim_commands(config, pim_provider)` give collections the same guarantees as mail: a fenced lease, blobs before events before cursors, replay protection, the started marker for commands. `run_commands` leaves calendar and contact commands (`put_object`, `delete_object`, `respond_object`) to `run_pim_commands`; an applied `put_object` or `respond_object` also journals the object as the server holds it. When an `AccountEntry` has a `pim` provider, the worker runs both after the mail run, with the account's mailbox filters left out (they name mailboxes, not collections); their errors are logged and do not fail the mail run.

## Scheduling

- **Incoming:** a synced message with a `text/calendar` part whose object has a `METHOD` is followed by `itip_received` (mailbox, item, the decoded part as a blob, and `skein_core::ItipSummary`). A quick byte scan skips messages without a calendar part. Nothing is applied: trusting and applying it is the consumer's decision. `Engine::without_message_inspection` turns this off, and with it `respond_invitation` (it fails with `unsupported`), for nodes that keep untrusted bytes out of their own process.
- **Commands with `notify`:** `put_object`, `delete_object` and `respond_object` ask the provider who schedules (`PimSession::scheduling`). Where the server does, the write carries `notify` and `schedule_result` says `server`. Where it does not, the engine reads the object before the write (for an organizer's change), writes with `notify` off, and mails what RFC 6638 asks of a scheduling agent through the account's sender: `REQUEST` to every attendee and `CANCEL` to removed ones for an organizer, `REPLY` to the organizer for an answer, all built with `skein-itip`, `From` the organizer's or attendee's address, `Date` and `DTSTAMP` from the command's time. `schedule_result` lists each message (`sent`, `failed` or `uncertain`, refused recipients), or says `none` with a reason (`not_organizer`, `not_a_scheduling_object`, `no_attendees`, `previous_unknown`, `attendee_not_found`, `organizer_not_scheduled`, `no_sender`). Messages are never retried; the marker reads `scheduling` while they go out, so a crash then is reported as `interrupted` and nothing is sent twice.
- **`respond_invitation`:** answers an invitation that came by mail. It runs on the mail path with the rules of `send` (retries while certainly not sent, `write_uncertain` once it may have left, `send_result`, `save_to_sent`), and the `REPLY` is built the same way on every try: `From` the attendee (named, or the one attendee in `To`/`Cc`, else `attendee_required`), `To` the organizer, `In-Reply-To` and `References` from the invitation.

## Waking an account

`wake_topic(account)` is the signal topic (`commands/{account}` in the tenant's group) the account's worker subscribes to: a hint on it runs pending commands, then a sync. `submit_command` publishes on it; composition roots use it to ask for a sync without spelling the topic.
